ElastiCache Amazon ElastiCache: Redis y Memcached

La capa de memoria delante de la base de datos: dos motores, dos estrategias de caching y la respuesta estándar a "reduce database load and latency".

Fase 5 · Bases de datos Dominio 3 · 24% Dominio 4 · 20%

Amazon ElastiCache es el servicio gestionado de in-memory data stores y cachés: despliega y opera clusters de Redis o Memcached sin que parchees, escales ni vigiles el software de caching tú mismo. Puedes empezar con una serverless cache o con clusters basados en nodos que dimensionas. El propósito de arquitectura es siempre el mismo: poner memoria delante de una base de datos más lenta o más cara, para que las lecturas repetidas se sirvan en microsegundos sin tocar RDS o DynamoDB. La documentación lo resume como "high-performance, scalable and cost-effective caching" eliminando la complejidad de desplegar un cache distribuido.

En el examen, ElastiCache aparece como componente de una arquitectura, casi nunca como tema aislado: la app hace GET a la caché, y solo en cache miss consulta la base de datos y recalcula. Las dos decisiones que debes dominar son el motor (Redis frente a Memcached) y la estrategia (lazy loading frente a write-through). Ambas son decisiones de trade-off — consistencia frente a simplicidad, acierto frente a costo de escritura — y los enunciados suelen describir el síntoma y esperar que tú nombres la cura.

Las dos estrategias: lazy loading y write-through

Con lazy loading (también cache-aside), la aplicación solo puebla la caché cuando falla una lectura: mira la caché, y si no está la clave, consulta la base de datos y escribe el resultado en la caché con un TTL. Su virtud es la eficiencia: solo se cachean los datos que alguien lee de verdad. Su defecto es el dato obsoleto: si la base cambia y nadie reescribe la entrada, la caché sigue devolviendo la versión vieja hasta que expira el TTL — la ventana de inconsistencia la define ese TTL, que es obligatorio usarlo por eso mismo. El patrón de examen es transparente: "data is stale after updates" o "read the latest data" delata un cache-aside sin TTL corto.

Con write-through, cada escritura de la aplicación actualiza la base de datos y la caché al mismo tiempo: los datos cacheados siempre están al día y la primera lectura después de escribir ya es un hit. Los costes son dos: escribes en la caché aunque nadie lea ese dato después (desperdicio si la tasa de relectura es baja) y, si un nodo de caché se reinicia, se vacía — por lo que en la práctica se combina con lazy loading para repoblar tras un miss. La respuesta de arquitectura madura y citada en el examen es la combinación de ambas: write-through para frescura en lo que se escribe y lazy loading con TTL para repoblar y limitar la vejez de todo lo demás.

Redis o Memcached: la elección del motor

Redis es la opción por defecto en arquitecturas modernas y casi siempre la respuesta correcta del examen. Soporta replicación con réplicas de lectura y automatic failover en Multi-AZ, persistencia — snapshots RDB y AOF — y backup/restore, además de estructuras enriquecidas: sorted sets para leaderboards, pub/sub, geospatial y hashes. Con cluster mode particiona los datos automáticamente entre shards (con réplica por shard), escalando escritura y lectura horizontalmente. Es, además, el session store por excelencia de aplicaciones multi-instancia: sesiones y contadores compartidos con TTL para expirar sesiones.

Memcached es deliberadamente simple: un cache de pares clave-valor multi-hilo, sin replicación, sin persistencia, sin backup ni failover — si un nodo muere, sus datos desaparecen y se repueblan como si fuera lazy loading puro. Esa simplicidad es su mérito: nodos grandes, coste contenido y paralelismo real para object caching simple. La regla de decisión que el examen explota: si el enunciado menciona alta disponibilidad, failover, persistencia, backups, sesiones o estructuras de datos ricas, la respuesta es Redis; si solo pide "simple, ephemeral key-value cache", Memcached puede aparecer como opción válida — y a veces como distractor frente a escenarios que exigen Redis.

El patrón session store merece mención propia porque es la pregunta de examen más común con Redis: cuando el Auto Scaling group lanza instancias nuevas o retira otras, las sesiones de usuario deben vivir en un almacén compartido, no en la memoria local de una instancia que puede desaparecer. Con Redis, la aplicación guarda cada objeto de sesión con un TTL y todo request lo lee de la caché; el TTL expira las sesiones abandonadas sin procesos de limpieza, y la replicación Multi-AZ evita perder el estado al perder un nodo. En Memcached ese patrón es posible pero frágil — sin replicación ni failover, la muerte de un nodo arrastra las sesiones que alojaba — y esa fragilidad es exactamente la razón por la que los enunciados con sesiones apuntan a Redis.

Para el examen
"Reduce load on the database / improve read latency" → ElastiCache (o DAX si la base es DynamoDB). "Stale data in cache" → lazy loading con TTL. "Cache always up to date after writes" → write-through. "Session store shared across instances" → Redis. "Leaderboard / sorted sets / pub/sub" → Redis. "Simple cache, no persistence needed" → puede ser Memcached. "Cache must survive node failure with failover" → Redis Multi-AZ.
Trampa clásica
Un cache no convierte tu base en "strongly consistent": si el enunciado exige leer siempre el último valor escrito, la caché es un distractor y la respuesta va por consistencia de la propia base. Y recuerda que DAX es específico de DynamoDB: para RDS, Aurora o APIs propias, la capa de memoria es ElastiCache.
Checkpoint — lo que debes recordar
  1. ElastiCache = Redis o Memcached gestionados, en modalidad serverless o por nodos.
  2. Lazy loading llena la caché tras un miss: eficiente pero permite datos obsoletos — mitiga con TTL.
  3. Write-through escribe caché y base a la vez: datos frescos garantizados, con costo de escrituras quizá inútiles.
  4. La estrategia madura es combinar ambas: write-through + lazy loading con TTL.
  5. Redis aporta replicación, failover Multi-AZ, persistencia, backups y estructuras ricas; Memcached es simple y volátil.
  6. Session store multi-instancia y leaderboards → Redis; cache de objetos efímero → Memcached.
