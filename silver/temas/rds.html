RDS Amazon Relational Database Service

La distinción entre Multi-AZ y read replicas es una de las preguntas más repetidas del examen: alta disponibilidad con réplica síncrona y pasiva frente a escala de lectura con réplica asíncrona y promocionable.

Fase 5 · Bases de datos Dominio 2 · 26% Dominio 3 · 24% Dominio 4 · 20%

Amazon RDS es el servicio gestionado de bases de datos relacionales: eliges un motor estándar — MySQL, PostgreSQL, MariaDB, Oracle, Microsoft SQL Server o Db2 — y AWS se encarga del undifferentiated heavy lifting: aprovisionar la infraestructura, parchear el sistema operativo y el motor, gestionar backups y alta disponibilidad. Sigues siendo responsable de lo que la documentación llama query tuning: el diseño del esquema, la distribución de datos y la optimización de consultas siguen siendo tuyos, con Performance Insights como herramienta para encontrar las consultas problemáticas. El acceso de red se controla con security groups, y la instancia queda dentro de una VPC con subnets por AZ.

Para el examen, RDS no se pregunta como producto sino como arquitectura de despliegue. Hay dos palancas de diseño que el enunciado a menudo mezcla a propósito: Multi-AZ, que replica la instancia en otra Availability Zone para sobrevivir a fallos de infraestructura, y read replicas, que descargan las lecturas de la primaria para escalar horizontalmente. Se parecen en el nombre y se diferencian en todo lo demás: propósito, tipo de replicación, si sirven tráfico y si se pueden promover. Confundirlas es el error más caro de esta área del temario, así que esta página se construye alrededor de esa distinción.

Multi-AZ: alta disponibilidad con standby síncrona

Un despliegue Multi-AZ DB instance mantiene una standby en otra Availability Zone de la misma región, replicada de forma síncrona. La standby es deliberadamente pasiva: no atiende consultas de clientes, solo recibe cambios, y su única razón de existir es tomar el relevo cuando la primaria falla. En un failover, RDS conmuta el nombre DNS de la instancia hacia la standby — las conexiones se reestablecen apuntando al mismo endpoint — en un proceso que típicamente se resuelve en el orden de un minuto. El enunciado que lo delata usa palabras como "resilient to database failures", "survive the loss of an Availability Zone" o "high availability", y la respuesta no añade réplicas legibles: solo la standby.

La variante moderna, Multi-AZ DB cluster, cambia la topología: dos standby en dos AZs adicionales (una writable y dos reader instances en tres zonas), que además de failover sí pueden servir tráfico de lectura a través de su propio endpoint. La documentación lo describe como "tres zonas" en la consola, frente al "Multi-AZ: Yes" de la instancia clásica de una sola standby. También importa el porqué del costo: Multi-AZ duplica (o triplica) el hardware sin añadir capacidad de lectura en el modo clásico — pagas disponibilidad, no rendimiento, y esa trade-off aparece en preguntas de optimización de costos. Finalmente, Multi-AZ es el prerrequisito natural para patching y mantenimiento sin downtime: los cambios se aplican primero a la standby, se conmuta, y luego a la antigua primaria.

Read replicas: escala de lectura asíncrona y promocionable

Una read replica es una copia de solo lectura que RDS construye con las capacidades de replicación nativas del motor. La replicación es asíncrona: la primaria confirma las escrituras sin esperar a la réplica, lo que evita el costo de latencia de Multi-AZ a cambio de una posible replication lag — lecturas eventualmente consistentes. La aplicación enruta las consultas de lectura al endpoint de la réplica, descargando a la primaria para que asuma más escrituras: el patrón de examen es "read-heavy workload" o "reporting queries are slowing down production". Puedes crear réplicas en otra AZ, en otra región (cross-region, con costo de transferencia de datos) o encadenar réplicas de réplicas, y una réplica existente puede promocionarse a instancia independiente — la herramienta de examen para "promote a replica to become a standalone database" o para migraciones con downtime mínimo.

El detalle que cierra la distinción: una read replica también puede ser origen de failover de DR, pero no es su función primaria, y sobre todo no conmuta sola: la promoción es una decisión tuya, explícita. Si el requisito es "automatic failover", la respuesta es Multi-AZ; si es "scale reads" o "serve reads closer to users", es read replica; y si el escenario pide ambas cosas, la arquitectura correcta es Multi-AZ + réplicas: standby para disponibilidad y réplicas para rendimiento, simultáneamente.

RDS Proxy: agrupar conexiones y sobrevivir al failover

Cada conexión de base de datos consume memoria y CPU en la instancia, y las arquitecturas serverless — Lambda por encima de todo — abren conexiones en ráfagas capaces de agotarlas. Amazon RDS Proxy interpone un connection pool totalmente gestionado entre la aplicación y la base de datos: las aplicaciones abren muchas conexiones al proxy, y el proxy las multiplexa sobre un conjunto pequeño de conexiones reales a RDS. El beneficio inmediato es la escala de conexiones; el segundo, y el más citado, es la resiliencia: en un failover Multi-AZ, el proxy detecta el cambio y reconecta a la nueva primaria conservando las conexiones de las aplicaciones, que no se enteran. En seguridad, RDS Proxy permite exigir IAM authentication a los clientes del proxy, y almacenar las credenciales de la base de datos en AWS Secrets Manager — eliminando contraseñas embebidas en el código.

Backups: automatizados, snapshots y point-in-time restore

RDS trae backup nativo en dos formas complementarias. Los automated backups ejecutan copias diarias durante una ventana configurable y además exportan los transaction logs cada pocos minutos, lo que habilita el point-in-time restore: recuperar la instancia al estado de cualquier segundo dentro del periodo de retención, configurable hasta 35 días. Los manual snapshots se toman cuando tú decides y persisten más allá de la vida de la instancia y de su retención — son la pieza para archivar estados, compartirlos entre cuentas o copiarlos a otra región. Para el diseño de DR recuerda la jerarquía: Multi-AZ protege contra fallos de infraestructura en minutos, backups automatizados contra corrupción de datos con grano fino, y los snapshots son tu copia duradera. La gestión de todos estos planes a escala de organización es trabajo de AWS Backup, que ya viste en la página de backup de esta fase.

Trampa clásica
Dos distractores recurrentes. Primero, usar una read replica como mecanismo de failover automático: la réplica no conmuta sola, y el enunciado que pide HA automática exige standby Multi-AZ. Segundo, "Multi-AZ improves performance": falso en el modo clásico — la standby no sirve lecturas y la replicación síncrona no acelera nada; quien promete más rendimiento de lecturas es el set de réplicas o el Multi-AZ DB cluster con reader instances.
Checkpoint — lo que debes recordar
  1. Multi-AZ = standby pasiva, replicación síncrona, failover automático vía DNS, misma región.
  2. Multi-AZ DB cluster = dos standbys en tres zonas, con reader instances que sí sirven lecturas.
  3. Read replica = asíncrona, sirve lecturas, escalable en AZ/región, promocionable a standalone.
  4. Si piden failover automático → Multi-AZ; si piden escala de lectura → réplicas; si piden ambas → los dos juntos.
  5. RDS Proxy: pool gestionado, preserva conexiones en failover, IAM auth y Secrets Manager.
  6. PITR con backups automatizados y transaction logs; retención hasta 35 días; snapshots manuales persisten indefinidamente.
  7. El query tuning sigue siendo responsabilidad tuya — RDS gestiona infraestructura, no tus consultas.
