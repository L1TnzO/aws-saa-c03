EFS y FSx Amazon Elastic File System · Amazon FSx

Los sistemas de archivos compartidos de AWS: cuando muchas instancias necesitan montar el mismo volumen a la vez, la respuesta no es EBS, es EFS o alguna variante de FSx.

Fase 4 · Almacenamiento Dominio 3 · 24% Dominio 4 · 20%

El block storage de EBS sirve a una instancia cada vez: un volumen no se comparte. Pero hay cargas — directorios home, shares de empresa, builds de código, render y HPC — donde decenas de máquinas deben leer y escribir el mismo árbol de archivos simultáneamente. Para eso existe el shared file storage: Amazon EFS ofrece un sistema NFS serverless que crece y encoge solo, y Amazon FSx es una familia de sistemas de archivos gestionados "purpose-built": FSx for Windows File Server para cargas SMB con Active Directory, FSx for Lustre para cómputo de alto rendimiento, y variantes como FSx for NetApp ONTAP y FSx for OpenZFS para casos de compatibilidad específicos.

La pregunta del examen casi nunca es "describe EFS": es "¿qué servicio de archivos elijo para este workload?". La regla de decisión tiene tres ramas: si tus servidores son Linux y hablan NFS, EFS; si tu empresa vive en Windows con SMB y Active Directory, FSx for Windows File Server; si el workload es HPC o machine learning con datasets masivos y latencia sub-milisegundo, FSx for Lustre. El costo de equivocarse es real: montar una share de Windows en decenas de instancias Linux, o intentar escalar HPC sobre NFS genérico, son soluciones frágiles que el examen penaliza.

Amazon EFS: el NFS serverless y elástico

EFS es totalmente elástico y sin servidores que gestionar: crece hasta petabytes a medida que añades archivos y se contrae al borrarlos, sin aprovisionar capacidad ni parchear nada. Habla NFSv4.1 y NFSv4.0, de modo que las herramientas Linux existentes funcionan sin cambios, y es accesible desde prácticamente todo el cómputo de AWS: EC2, ECS, EKS, Lambda y Fargate. Cada AZ de la VPC recibe un mount target que evita el tráfico cruzado entre AZs al montar. Para el acceso, combina IAM con security groups, y puedes cifrar los datos en descanso (con claves KMS, activado al crear el file system) y en tránsito (al montar), además de soportar permisos POSIX a nivel de archivo.

En diseño hay dos elecciones. La primera es el tipo de file system: Regional — el recomendado — replica los datos redundántemente en múltiples AZs separadas geográficamente, de modo que la pérdida de una AZ no interrumpe el servicio; One Zone guarda todo en una sola AZ y es la opción de ahorro cuando los datos son reproducibles. La segunda es el modo de rendimiento: para la mayoría de workloads la guía oficial recomienda General Purpose (latencia baja para web serving, CMS y home directories) con throughput Elastic, que escala automáticamente con la actividad. Las lifecycle policies de EFS añaden un ahorro importante: mueven archivos poco accedidos a tiers IA y Archive dentro del propio file system, reduciendo el costo por GB.

FSx for Windows File Server: SMB nativo y Active Directory

FSx for Windows File Server es un file server de Windows completamente gestionado y nativo, con soporte del protocolo SMB (versiones 2.0 a 3.1.1), NTFS real y Active Directory para autenticar usuarios y aplicar ACLs de Windows a archivos y carpetas. Es la respuesta a "lift and shift" de aplicaciones empresariales: business apps, home directories de usuarios Windows, content management y shares departamentales siguen funcionando sin cambios porque la compatibilidad es a nivel de herramienta y permisos. La familia ofrece discos SSD — para bases de datos y media processing con latencias sub-milisegundo consistentes — y HDD más económicos para shares generales, con storage, SSD IOPS y throughput aprovisionables de forma independiente.

En disponibilidad, FSx para Windows replica el patrón Multi-AZ que ya conoces de RDS: los file systems Multi-AZ mantienen un file server standby en otra AZ con failover automático, mientras que los Single-AZ solo se protegen contra fallos de componentes dentro de la AZ. Los backups son diarios, automáticos por defecto, incrementales y consistentes a nivel de file system gracias a VSS. Se cifra en descanso con KMS y en tránsito con Kerberos de SMB, y se puede acceder desde on-premises a través de Direct Connect o Site-to-Site VPN, o desde otras VPCs, cuentas o regiones mediante VPC peering o Transit Gateway. Ese acceso híbrido es la clave de muchas preguntas de migración.

FSx for Lustre y la familia FSx

FSx for Lustre es el file system para high performance computing: cómputo masivamente paralelo con latencias sub-milisegundo y throughput de cientos de GB/s, usado en simulaciones, render y entrenamiento de modelos de machine learning. Su truco estrella es la integración con S3: enlazas el file system a un bucket S3, Lustre materializa los objetos como archivos a alta velocidad, las miles de workers procesan en paralelo, y los resultados vuelven a escribirse en S3. Los despliegues scratch son temporales y óptimos en costo para procesado corto; los persistent mantienen réplicas de datos y sirven para cargas de más larga vida. La familia completa — NetApp ONTAP para migrar NAS con protocolos múltiples, OpenZFS para snapshots y clones con compatibilidad ZFS — amplía la matriz de elección, pero en SAA-C03 el foco es la tríada Windows/Lustre/EFS.

Para el examen
"Shared file system across many Linux instances / containers" → EFS (Regional si piden HA, One Zone si priorizan costo). "Windows workloads, SMB shares, Active Directory users and ACLs" → FSx for Windows File Server (Multi-AZ si mencionan failover). "High performance computing / machine learning over data in S3" → FSx for Lustre. "Block storage for a single EC2 instance" → EBS, que no es compartible — el distractor favorito.
Trampa clásica
EBS Multi-Attach existe, pero es una excepción para instancias concretas, no un file system compartido: cuando el enunciado dice "many instances must read and write the same files simultaneously", la respuesta de arquitectura es EFS o FSx, no "attach the EBS volume to all instances". Y si el escenario menciona "Windows domain users and file-level permissions", Active Directory + ACLs descartan EFS.
Checkpoint — lo que debes recordar
  1. EFS = NFS serverless: crece a petabytes solo; recomendado Regional y General Purpose + Elastic throughput.
  2. Cada AZ tiene su mount target; el acceso se controla con IAM + security groups y cifrado en tránsito y en descanso.
  3. EFS One Zone para ahorrar con datos reproducibles; Regional para alta disponibilidad real.
  4. FSx Windows = SMB + Active Directory + ACLs, con backups VSS diarios y acceso híbrido vía DX/VPN.
  5. FSx Lustre para HPC/ML: latencia sub-ms y carga del dataset desde S3; scratch vs persistent.
  6. File storage compartido ≠ EBS: el volumen EBS es de una instancia (salvo Multi-Attach puntual).
