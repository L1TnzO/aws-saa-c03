CloudTrail y Config AWS CloudTrail, AWS Config

Auditoría y governance: CloudTrail graba quién llamó a qué API y cuándo; Config retrata cómo estaban configurados tus recursos y detecta el drift.

Fase 7 · Seguridad y gobernanza Dominio 1 · 30% Auditoría, compliance y drift

Aquí va la analogía que resuelve medio examen: CloudTrail es la cámara de videovigilancia de la cuenta — registra cada llamada a la API (quién la hizo, qué operación, desde qué IP, a qué hora) como un evento inmutable que se archiva en S3; AWS Config es el fotógrafo forense — no le importa la llamada en sí, sino el estado resultante: cómo estaba configurado cada recurso, cómo se relaciona con otros y cómo cambió esa configuración a lo largo del tiempo. Cuando ocurre un incidente, la secuencia de investigación clásica es: Config te dice "qué tenía abierto el security group aquel día" y CloudTrail te dice "quién lo abrió y cuándo".

El examen separa ambos con una pregunta simple: ¿te piden acciones o configuraciones? "Audit API activity", "who deleted the bucket", "record user activity" → CloudTrail. "Track configuration changes", "detect noncompliant resources", "historical configuration of an IAM policy" → Config. La combinación de los dos — más un bucket S3 central y Alerting con EventBridge — es la respuesta estándar a casi cualquier escenario de governance multi-cuenta.

CloudTrail: el registro inmutable de la actividad de la cuenta

Cada operación de AWS es una llamada a una API, y CloudTrail la convierte en un evento: identidad del llamador, hora, región, IP de origen, parámetros y respuesta. Conviene distinguir los management events — las operaciones del control plane como CreateBucket, RunInstances o toda la gestión de IAM, que se registran por defecto — de los data events — operaciones sobre los datos en sí, como GetObject en S3 o invocaciones de Lambda, de alto volumen y no activos por defecto, porque encarecen el trail. La consola ofrece gratis un Event History de los últimos 90 días; para retención mayor y cobertura completa se crea un trail multi-Región que entrega los log files a un bucket S3 tuyo.

El patrón de examen es el organization trail: creado desde la cuenta de management de AWS Organizations, replica el trail en todas las cuentas miembro y centraliza los logs en un único bucket, de modo que ni los administradores de las cuentas hijas puedan borrar la evidencia. Dos endurecimientos clásicos: la log file validation, que firma cada archivo con hash para detectar manipulación del log, y los Insights events, que analizan la actividad de management inusual (picos de llamadas, errores de permisos masivos) para señalar actividad anómala. Desde el trail también se replica a CloudWatch Logs y EventBridge para alertar en (casi) tiempo real.

AWS Config: el estado y el drift de cada recurso

AWS Config proporciona una vista detallada de la configuración de los recursos de la cuenta: cómo están relacionados entre sí y cómo estaban configurados en el pasado, para ver cómo cambian en el tiempo. Cada recurso soportado — una instancia EC2, un volumen EBS, un security group, una VPC — queda descrito como configuration item con su línea temporal. Sobre esa base, Config responde los cuatro escenarios de su documentación: administración de recursos (visibilidad de quién creó, modificó o borró algo sin hacer polling), auditoría y compliance (la configuración histórica como evidencia), troubleshooting (relaciones entre recursos y la última configuración buena) y análisis de seguridad — puedes ver, por ejemplo, qué política IAM tenía un usuario o qué puertos tenía abiertos un security group en una fecha concreta.

La pieza más preguntada son las Config rules: condiciones con las que Config evalúa continuamente tus recursos conforme se crean, cambian o se borran, marcándolos compliant o noncompliant y notificando (SNS) cuando alguien viola una regla — el mecanismo exacto de drift detection con remediación: reglas agrupadas en conformance packs, remediation automática para recursos noncompliant y aggregators que consolidan inventario y compliance de múltiples cuentas y Regiones en una sola. Config también permite consultar el estado actual de los recursos con advanced queries (SQL).

Para el examen
En escenarios multi-cuenta, la respuesta de governance suele ser la cadena completa: Organizations + organization trail + bucket S3 central + Config aggregator. Si añaden "y quiero alertar cuando algo esté fuera de compliance", completa con Config rules + SNS/EventBridge; si añaden "postura de seguridad frente a CIS/PCI", la pieza es Security Hub, que se alimenta de ambos. Recuerda que el Event History de 90 días de la consola no sustituye a un trail persistente.
Trampa clásica
Dos cruces habituales: elegir CloudTrail para "detect configuration drift" (eso es Config) y elegir Config para "who made the API call" (eso es CloudTrail). También hay distractores con CloudWatch: CloudWatch monitoriza métricas y logs de aplicaciones; la auditoría de la API de AWS es territorio de CloudTrail. Y ojo: data events de S3/Lambda no se registran por defecto — si el enunciado pregunta "who read this object", la respuesta incluye activar data events.
Checkpoint — lo que debes recordar
  1. CloudTrail = auditoría de acciones: cada API call como evento (quién, qué, cuándo, desde qué IP).
  2. Management events por defecto; data events (S3 objeto, Lambda) opcionales y de coste alto; Insights para actividad inusual.
  3. El organization trail cubre todas las cuentas y centraliza la evidencia en un bucket.
  4. log file validation firma los archivos para detectar manipulación.
  5. Config = estado y drift: configuration items con historia, relaciones y timeline.
  6. Config rules evalúan compliance continuo; con conformance packs, remediation y aggregators multi-cuenta.
  7. Responden preguntas distintas: acciones → CloudTrail; configuraciones → Config.
