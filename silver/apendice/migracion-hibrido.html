Migración e híbridoApéndice · D3-D4

Mover cargas y datos a AWS — o mantener un pie en cada mundo — tiene su propia caja de herramientas: las 6R, DMS, DataSync, Snow Family y MGN. El examen te pone un volumen de datos, un plazo y una ventana de downtime, y espera que elijas la herramienta exacta en segundos.

Task Statement oficial 4.1
Design cost-optimized storage solutions
Skills: determining the lowest cost method of transferring data to AWS storage · selecting the appropriate service for data migration — Knowledge (3.3/4.3): database engines with appropriate use cases (homogeneous vs heterogeneous migrations)

1Estrategia: las 6R de la migración

Antes de elegir herramientas, AWS enmarca toda migración en seis estrategias — las famosas 6R. Ninguna es "la correcta" en abstracto: la elección depende de la urgencia, el presupuesto y cuánto valor estratégico tiene modernizar cada aplicación. Un portafolio real combina varias a la vez, porque no todas las apps merecen la misma inversión. En el examen, el enunciado suele dar la pista con frases como as quickly as possible (rehost) o take advantage of cloud-native features (refactor).

EstrategiaQué significaCuándo elegirla
Rehost — lift-and-shiftMover la app tal cual a IaaS (EC2), sin tocar códigoPlazos cortos, presupuesto ajustado, hyperscale rápido; se ejecuta con AWS MGN
Replatform — lift-tinker-and-shiftCambios puntuales sin re-arquitectura (self-managed MySQL → RDS, VMs → contenedores)Algo de margen temporal y ganas de bajar carga operativa ya
Refactor / re-architectRediseñar para cloud-native (monolito → microservicios + serverless)Modernización estratégica; el mayor costo y el mayor beneficio a largo plazo
RepurchaseAbandonar la app y comprar SaaS equivalenteCRMs, HR, mail: la funcionalidad ya existe como servicio
RetireApagar lo que ya nadie usaAWS estima que ~20% del portafolio empresarial es candidato; elimina costo puro
Retain (revisit)Dejarlo on-prem por ahoraRegulatorio, dependencias duras o TCO que no compensa; "no todo se migra"

Marco de referencia de migración de AWS (6R) — base de las preguntas de estrategia.

Señales del examen

migrate quickly with the least effort / no code changes → rehost (MGN). move to managed database with minimal changes → replatform (RDS/Aurora). decouple and modernize into microservices → refactor. Y ojo: si la pregunta da una fecha límite y pide cero cambios de aplicación, la respuesta nunca es refactor — por atractiva que parezca la arquitectura propuesta.

La estrategia 6R se apoya en las guías oficiales de migración de la capa bronze; para el detalle de herramientas sigue leyendo: ../../bronze/05-docs/migration-mgn/what-is-mgn.md (rehost automatizado) y ../../bronze/05-docs/migration-dms/chap-introduction-sources.md (replatform de bases de datos).

2AWS DMS: migrar bases de datos con mínimo downtime

AWS Database Migration Service (DMS) mueve datos entre bases de origen y destino casi siempre distintas: motores relacionales, NoSQL, data warehouses e incluso S3 o Kinesis como destino. Su arquitectura tiene tres piezas: un replication instance (EC2 administrado), los endpoints de origen y destino, y las tasks que definen qué tablas mover. La distinción clave del examen es homogeneous vs heterogeneous: si el motor no cambia (Oracle → Oracle, MySQL → Aurora MySQL), la migración es homogénea y DMS basta; si el motor cambia (Oracle → Aurora PostgreSQL), el esquema y el código deben convertirlos antes con otra herramienta.

Esa herramienta es la AWS Schema Conversion Tool (SCT): analiza el esquema origen, convierte tipos y objetos (PL/SQL → PL/pgSQL), estima el esfuerzo con un assessment report y también convierte warehouses (Teradata/Oracle → Redshift). SCT prepara el terreno; DMS transporta los datos. Para volúmenes enormes, SCT puede extraer a S3 y DMS cargar desde ahí — pero ese es un matiz avanzado que rara vez decide la respuesta.

DimensiónHomogénea (mismo motor)Heterogénea (otro motor)
Ejemplo típicoOracle on-prem → RDS Oracle; MySQL → Aurora MySQLOracle → Aurora PostgreSQL; SQL Server → RDS MySQL
¿Necesita SCT?No (esquema ya compatible; opcional para assessment)Sí: convierte esquema, tipos y código almacenado antes de mover datos
Rol de DMSMover datos (full load ± CDC)Mover datos una vez el esquema destino existe
Riesgo típicoBajoIncompatibilidades de tipos/features sin equivalente

CDC: la magia del mínimo downtime

La característica que convierte a DMS en la respuesta estrella es el change data capture (CDC). DMS lee los cambios directamente de los logs de transacciones nativos del motor (redo logs de Oracle, binlogs de MySQL, WAL de PostgreSQL) y los replica al destino. Con el modo full load + CDC, DMS copia primero todos los datos existentes y luego mantiene el destino sincronizado con los cambios que siguen llegando a producción: la app sigue funcionando contra el origen hasta el momento elegido. El cutover final es solo redirigir la aplicación — una ventana de minutos, no de horas. Por eso, ante migrate a database with minimal downtime, la respuesta es DMS con CDC (y SCT delante si hay cambio de motor).

Modo de taskQué haceCuándo usarlo
Full load onlyCopia los datos existentes una vezMigraciones con ventana de mantenimiento amplia
Full load + CDCCopia inicial + replicación continua de cambiosMínimo downtime (la respuesta típica del examen)
CDC onlyReplica solo los cambios posteriores a un punto dadoTras una carga hecha con otra herramienta (dump previo)

Fuente: bronze/05-docs/migration-dms/chap-task-cdc.md.

Error común

Elegir DMS para "convertir" el esquema en una migración heterogénea: DMS mueve datos, no traduce esquemas ni procedimientos almacenados — eso es SCT. La trampa inversa también existe: usar SCT solo y esperar que mueva los datos en vivo. La pareja completa es SCT (esquema/código) + DMS (datos).

3DataSync y Transfer Family: mover archivos por la red

AWS DataSync automatiza transferencias de archivos/objetos entre NFS, SMB, HDFS u object storage on-premises (u otras nubes) y servicios AWS: S3, EFS y toda la familia FSx. El agente — una VM que despliegas junto a tus datos, cuando el origen es on-premises — mueve hasta 10 Gbps por agente con un protocolo paralelo propio. Las tasks definen origen, destino, filtros y scheduling (recurrente, tipo cron) y pueden verificar la integridad de todo lo transferido con checksums en tránsito y opcionalmente al final. Entre servicios de AWS (p. ej. S3 → EFS) no hace falta agente. Es la respuesta estándar a move active datasets over the network into AWS.

AWS Transfer Family resuelve un problema distinto: terceros o partners que siguen usando protocolos FTP. Crea endpoints SFTP, FTPS o FTP totalmente administrados cuyos usuarios autentican contra usuarios gestionados del servicio, IAM o tu IdP (AD/LDAP vía Directory Service) — y cuyos archivos caen directamente en S3 o EFS. Es la respuesta a third parties deliver files over SFTP, no code changes: mantienes el protocolo, cambias el backend a S3.

DimensiónAWS DataSyncAWS Transfer Family
ProblemaMover grandes volúmenes de datos de A a BAceptar archivos por protocolos FTP/SFTP gestionados
ProtocolosNFS, SMB, HDFS, object storage ↔ S3/EFS/FSxSFTP, FTPS, FTP (endpoints públicos o en tu VPC)
Componente claveAgente on-premises (10 Gbps c/u; sin agente AWS↔AWS)Endpoint + usuarios autenticados (servicio, IAM o AD/IdP)
GarantíasCifrado en tránsito + verificación de integridad; tasks programablesGestión de identidad y archivos entregados en S3/EFS
Señal del examenbulk migration / scheduled copy / verify integritypartners still use SFTP

Fuente: bronze/05-docs/migration-datasync/what-is-datasync.md + bronze/04-faqs/aws-transfer-family.md.

Señales del examen

ongoing nightly copy between on-premises NFS and EFS → DataSync con scheduling. validate that all files arrived intact → DataSync (integrity verification). existing SFTP workflow, want storage in S3 → Transfer Family. Distinción rápida: DataSync mueve datos; Transfer Family expone un protocolo sobre almacenamiento AWS.

4Snow Family: cuando la red no llega

Cuando el volumen de datos es tan grande que la red se vuelve el cuello de botella, AWS lo resuelve con logística: Snow Family son dispositivos físicos que AWS te envía por mensajería, llenas offline en tu data center y devuelves — los datos aparecen en tu bucket S3 sin consumir tu ancho de banda. Todos cifran los datos en reposo y en tránsito físico (KMS), y soportan jobs de import (a S3) y export (desde S3). La regla que repite el examen: si por la red tardarías más de una semana, muévelo con Snow.

DispositivoCapacidadSu señal del examen
Snowcone8 TB utilizables (HDD); ~2 kg, cabe en una mochila, puede correr con bateríaPocos TB, sitios remotos o sin espacio/rack; edge computing ligero
Snowball Edge Storage Optimized80 TB utilizables (dato canónico del examen; los dispositivos actuales llegan a 210 TB), 40 vCPUEl clásico: decenas de TB o la red tardaría > 1 semana
Snowball Edge Compute Optimized42 TB utilizables + opción de GPU y más vCPUComputo local intensivo además del transporte (edge, pre-procesado en el dispositivo)
SnowmobileHasta 100 PB por contenedor rodante; exabytes agregando viajesMigraciones de data center completo; videotecas, genómica

Fuente: bronze/05-docs/migration-snow/whatisedge.md (nota: la guía indica que Snowball Edge ya no acepta clientes nuevos a favor de DataSync/alternativas — el examen sigue usando el canon clásico).

¿Cuánto tarda subir X TB a Y Mbps?

El examen te lo pide con números: la fórmula es tiempo = TB × 8 × 10¹² bits ÷ (velocidad en bit/s). Un truco rápido: a 1 Gbps teóricos, 10 TB tardan ~22 horas; como el rendimiento real ronda el 80%, calcula con margen. La tabla muestra el razonamiento que espera la pregunta — y por qué 100 TB con enlaces modestos se convierte en trabajo para Snowball.

VolumenEnlaceTiempo teóricoHerramienta razonable
10 TB1 Gbps~22 hDataSync online
100 TB1 Gbps~9,3 días > 1 semanaSnowball Edge
100 TB100 Mbps~93 díasSnowball Edge (ni lo intentes online)
100 TB10 Gbps (Direct Connect)~22 hDataSync online
5 PBcualquiera razonablemesesSnowmobile

Cálculo: segundos = TB × 8 × 10¹² ÷ Mbps × 10⁶. Ejemplo 100 TB @ 1 Gbps: 800.000 s ≈ 9,3 días.

Señales del examen

move 100 TB within one week, limited bandwidth → Snowball Edge. migrate an entire data center (petabytes) → Snowmobile. small site, no rack space, few TB → Snowcone. Si el enunciado da un enlace potente y tiempo de sobra, la respuesta pasa a ser DataSync — Snow cobra por job y días de posesión, así que no lo elijas si la red llega.

5AWS MGN y el descubrimiento del portafolio

AWS Application Migration Service (MGN) — rebautizado recientemente como AWS Transform MGN, aunque el examen lo sigue llamando MGN — es la herramienta oficial del rehost. Instalas un agente en cada servidor (físico, virtual o incluso en otra nube) y MGN inicia una replicación continua a nivel de bloque hacia un staging area de bajo costo en AWS (volúmenes EBS baratos + snapshots). La producción no se detiene. Cuando quieras, lanzas instancias de test desde las réplicas para validar aplicaciones sin tocar nada, y el día del cutover real solo cortas el tráfico: la ventana es de minutos. Tres templates (replication, launch y post-launch) controlan el comportamiento por servidor, y los servidores se agrupan en aplicaciones y waves para operar migraciones de miles de máquinas.

Antes de migrar hay que saber qué se migra: AWS Application Discovery Service recoge el inventario on-premises de dos formas — el Discovery Connector (agentless, se conecta a VMware vCenter y levanta inventario de VMs) y el Discovery Agent (se instala en cada máquina para datos más finos de uso de CPU/memoria/red). Todos los hallazgos confluyen en AWS Migration Hub, el panel único que agrega el estado de las migraciones aunque uses MGN para servidores, DMS para bases de datos y DataSync para archivos — un solo lugar para seguir el progreso de todo el portafolio.

HerramientaRol en la migraciónDato que la delata
Application Discovery ServiceInventario y dependencias del data centerConnector (agentless, vCenter) vs Agent (por servidor)
Migration HubPanel agregado de todo el programa de migraciónUna sola vista aunque mezcles MGN + DMS + DataSync
AWS MGNRehost automatizado de servidores a EC2Replicación continua + cutover de minutos; sustituyó a Server Migration Service

Fuente: bronze/05-docs/migration-mgn/what-is-mgn.md + bronze/04-faqs/aws-application-migration-service-mgn.md.

Señales del examen

migrate 500 servers to EC2 with minimal downtime, test before cutover → MGN. discover on-premises environment / build inventory → Application Discovery Service. single view of migration status across tools → Migration Hub. Trampa: DMS migra bases de datos, MGN migra servidores completos — si la pregunta habla de la app entera sobre EC2, es MGN.

6El mundo híbrido: Outposts, DX y VPN

Para cerrar, la pieza de conectividad. AWS Outposts es hardware físico de AWS instalado en tu data center y administrado por AWS: ejecuta servicios nativos (EC2, EBS, S3 on Outposts, RDS en variantes rack) con las mismas APIs, consola y herramientas que usas en la Región. Se elige cuando necesitas latencias de milisegundo único hacia sistemas on-premises o requisitos de data residency que obligan a procesar los datos en tu edificio, manteniendo la experiencia operativa de la nube. Existe en formato rack (42U) y servers (1U/2U) para oficinas o tiendas pequeñas.

Para el enlace de red entre tu data center y tu VPC, todo el detalle — Site-to-Site VPN, Direct Connect (dedicado 1/10 Gbps), DX Gateway, y los patrones de failover VPN+DX — lo tratamos a fondo en la página Redes y conectividad del apéndice. Y para los datos, este mismo capítulo te acaba de dar el resto del mapa: Storage Gateway para acceso continuo de baja latencia, DataSync para mover por la red, Snow para volúmenes que no caben en el calendario.

Síntesis operativa de toda esta página: cada fila es un reflejo de examen.

Los reflejos de migración del SAA-C03

1) "move 100 TB in a week, the WAN is slow" → Snowball Edge. 2) "migrate the database with minimal downtime" → DMS con CDC (full load + ongoing replication). 3) "partners already use SFTP" → Transfer Family sobre S3. 4) "migrate hundreds of servers, test first, minutes of cutover" → MGN. 5) "scheduled copy with integrity verification" → DataSync. Con estos cinco reflejos respondes casi cualquier pregunta de migración del blueprint.

Tip de estudio

Los números de Snow Family (8 / 42 / 80 TB, 100 PB) y los tiempos de recuperación de Glacier de la página anterior son el tipo de dato que el examen asume "sabido": no aparece en el enunciado, solo en las opciones. Dedícales una tarjeta de memoria propia a la pareja Snow↔volumen y otra a la pareja herramienta↔señal de esta sección.
