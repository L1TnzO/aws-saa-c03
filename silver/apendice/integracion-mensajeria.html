Integración, mensajería y APIsD2 · loosely coupled

Colas, topics, eventos, workflows y APIs: los cinco servicios de integración que hacen que una arquitectura sea loosely coupled. Esta página los cubre en profundidad de examen: SQS, SNS, EventBridge, Step Functions, Amazon MQ y API Gateway con AppSync.

Task Statement oficial 2.1
Design scalable and loosely coupled architectures
Knowledge: API creation and management (API Gateway), event-driven architectures, queuing and messaging (publish/subscribe), workflow orchestration (Step Functions), serverless patterns · Skills: designing event-driven and multi-tier architectures, determining the AWS services required to achieve loose coupling

1Por qué desacoplar: el espectro de comunicación

Cuando dos componentes se llaman directamente, el destino de uno depende del otro: si el consumidor cae, se ralentiza o simplemente está ocupado, el productor sufre. Desacoplar significa insertar una capa intermedia administrada que absorba fallos, picos y despliegues independientes; el examen lo delata con la frase decouple o loosely coupled. En AWS no existe una única forma de desacoplar: existe un espectro de primitivas de comunicación que se diferencian por quién responde, quién guarda el estado y qué garantía ofrecen. Elegir bien esa primitiva es exactamente la decisión que evalúa el Dominio 2.

En un extremo está la llamada síncrona request/response: el cliente pide y espera una respuesta — API Gateway es la puerta de entrada típica. En el medio están los mensajes (SQS: el consumidor hace pull de una cola cuando puede) y los eventos (SNS/EventBridge: el sistema push notifica a los interesados sin esperar respuesta). En el otro extremo está la orquestación de varios pasos con lógica de negocio, garantías duraderas y manejo de errores: un workflow en Step Functions. La regla mental: si necesitas respuesta inmediata → API; si necesitas trabajo diferido y fiable → mensaje; si solo notificas que algo pasó → evento; si hay un proceso de varios pasos con decisiones → workflow.

Tip de estudio

Memoriza el espectro como una línea de «necesito respuesta» a «necesito proceso»: sync → async → event-driven → orchestration. Cada pregunta de desacople del examen te está preguntando en qué punto del espectro cae el escenario.

2Amazon SQS: la cola enciclopédica

Amazon SQS es una cola hospedada, segura, duradera y disponible: los mensajes se replican en múltiples servidores y Availability Zones. Un productor envía mensajes a la cola y uno o más consumidores los extraen cuando pueden; los mensajes viven hasta 14 días (retención por defecto de 4 días) y su tamaño máximo es de 256 KiB, ampliable a prácticamente cualquier tamaño guardando el contenido en S3 y dejando solo el puntero en la cola. SQS escala de forma transparente ante spikes de carga sin aprovisionar nada, lo que lo convierte en la respuesta estándar a «absorber tráfico repentino sin perder peticiones».

Standard vs FIFO: la tabla que cae en el examen

SQS ofrece dos sabores de cola y la diferencia es tan examinable como conceptual. Standard prioriza throughput casi ilimitada a cambio de relajar dos garantías: at-least-once delivery (un mensaje puede llegar más de una vez, diseña operaciones idempotent) y best-effort ordering (el orden no está garantizado). FIFO (sufijo .fifo) prioriza el orden y la unicidad: los mensajes se agrupan por MessageGroupId — se garantiza el orden dentro de cada grupo y los grupos se procesan en paralelo — y se elimina la duplicación con un MessageDeduplicationId explícito o con content-based deduplication (hash SHA-256 del contenido, ventana de 5 minutos). El precio es la capacidad: 300 llamadas API/segundo, que suben a 3.000 TPS con batching (lotes de 10) y hasta 30.000 TPS habilitando el modo high-throughput FIFO (con orden relajada dentro del grupo).

Visibility timeout, polling y delay

El visibility timeout es el mecanismo anti-duplicado de SQS: cuando un consumidor recibe un mensaje, este se vuelve invisible al resto de consumidores durante ese tiempo (por defecto 30 segundos); si el consumidor termina y borra el mensaje (DeleteMessage), desaparece, pero si el timeout expira sin borrado, el mensaje vuelve a ser visible y otro consumidor lo recibirá de nuevo. Por eso la regla de oro: el visibility timeout debe ser mayor que el peor tiempo de procesamiento del consumidor — y con Lambda como consumidor, AWS recomienda configurarlo al menos 6 veces el timeout de la función. Puedes ajustarlo por mensaje con ChangeMessageVisibility.

Para recibir mensajes hay dos modos. El short polling (por defecto) consulta un subconjunto aleatorio de servidores y responde de inmediato, incluso vacío: gasta llamadas y puede dar respuestas vacías falsas. El long polling (WaitTimeSeconds > 0, hasta 20 segundos) consulta todos los servidores y espera hasta que haya mensajes: reduce costos y latencia efectiva, y es la opción correcta «para reducir respuestas vacías». Finalmente, los delay seconds (0–15 minutos) hacen que un mensaje nuevo sea invisible durante un tiempo; una delay queue aplica ese retraso a todos sus mensajes — útil para reintentos diferidos o tareas programadas a corto plazo.

Dead-letter queues y consumidores Lambda

¿Y si un mensaje falla siempre? Sin remedio, quedaría reingresado en bucle eterno. La dead-letter queue (DLQ) es una cola destino — de la misma cuenta y región, y con el mismo tipo (Standard→Standard, FIFO→FIFO) — a la que SQS mueve los mensajes tras superar maxReceiveCount recepciones sin borrado, definido en la redrive policy. La DLQ no es un cubo de basura: es la herramienta de depuración, porque aísla los mensajes problemáticos para inspeccionarlos, alarma con CloudWatch y eventualmente reintenta con redrive. Buena práctica: la retención de la DLQ debe ser más larga que la de la cola origen. Cuando el consumidor es una función Lambda, el event source mapping hace long polling de la cola por ti, escala la concurrencia automáticamente y procesa en lotes (batch size configurable por mensaje); si el lote entero falla, puedes enrutarlo entero a la DLQ con batch failover.

Señales del examen

"exactly-once" en SQS FIFO significa processing (procesado una vez), no delivery — la distracción clásica. Si la pregunta muestra consumidores lentos que re-procesan mensajes, la respuesta casi siempre es increase the visibility timeout. Si habla de empty responses o costos de polling, es long polling. Y si hay spikes de tráfico que no debe perderse, SQS es el buffer.

3Amazon SNS: topics y fan-out

Amazon SNS es el servicio publish/subscribe administrado: los publicadores envían mensajes a un topic — el canal lógico de comunicación — y SNS entrega una copia a cada suscriptor. Es push puro: el publicador no conoce a los consumidores ni espera respuesta. Un topic puede entregar a endpoints A2A (SQS, Lambda, HTTP/S, Firehose, y proveedores como Datadog o Splunk) y A2P (email, SMS, mobile push) en paralelo. El patrón estrella es el fan-out: un topic SNS con varias colas SQS suscritas; cada cola recibe su copia idéntica del mensaje y cada equipo consume a su ritmo. Combinado con filter policies, cada suscripción recibe solo lo que le importa.

Una filter policy es un JSON adjunto a la suscripción que SNS evalúa contra los message attributes del mensaje (por defecto) o contra el cuerpo con FilterPolicyScope = MessageBody. Ejemplo: {"event-type": ["order-placed"]} hace que esa suscripción solo reciba mensajes cuyo atributo event-type valga exactamente eso. Aquí conviene distinguir los message attributes (metadatos clave/valor que viajan fuera del payload; son los que filtran SNS y SQS, y no cuentan hacia el límite de 256 KiB) del payload (el contenido real del mensaje). Los topics también pueden ser FIFO: un FIFO topic garantiza orden por MessageGroupId y deduplicación, pero solo acepta suscriptores que sean colas SQS FIFO — no Lambda, ni HTTP, ni email.

Error común

Colocar un topic SNS FIFO con suscriptores Standard «para tener orden»: los suscriptores de un FIFO topic deben ser SQS FIFO. Otro clásico: usar el payload para filtrar cuando los message attributes existen justamente para eso (y viceversa: olvidar el FilterPolicyScope al filtrar por body).

4Amazon EventBridge: el bus de eventos

EventBridge es el servicio serverless de enrutamiento de eventos: aplica el modelo event-driven architecture con ingesta, filtrado, transformación y entrega. Su pieza central es el event bus: el default bus recibe automáticamente los eventos de los servicios AWS de tu cuenta; los custom buses reciben los eventos de tus aplicaciones; y los partner event sources traen eventos de SaaS (Auth0, Datadog, Zendesk…) sin escribir código de ingesta. Sobre el bus se definen rules: una regla es un event pattern JSON que compara campos del evento (por ejemplo {"source": ["aws.ec2"], "detail-type": ["EC2 Instance State-change Notification"]}) y enruta las coincidencias a más de 15 tipos de targets: Lambda, SQS, SNS, Step Functions, ECS, Kinesis, CodePipeline… El routing deja de estar en tu código y pasa a ser configuración declarativa.

EventBridge es más que buses. EventBridge Scheduler crea tareas programadas (one-time o recurrentes con cron/rate) a escala de millones de schedules con reintentos y ventanas flexibles — es el reemplazo recomendado de las reglas programadas. EventBridge Pipes resuelve el punto a punto: un solo origen (SQS, Kinesis, streams de DynamoDB, MSK) → filtro opcional → enrichment (Lambda o Step Functions enriquecen el evento) → un solo destino, sin escribir el pegamento. Y archive guarda los eventos del bus para replay: reproducir el pasado tras un bug o desplegar un consumidor nuevo y «reprocesar la historia».

5Step Functions y Amazon MQ

AWS Step Functions orquesta workflows de varios pasos con un lenguaje JSON declarativo (el Amazon States Language, ASL). El workflow se define como una state machine cuyos states se dividen en dos familias: Task (hacen trabajo llamando a Lambda o a más de 200 APIs de servicios AWS) y flow states que controlan el flujo: Choice decide por condición, Wait pausa, Parallel abre ramas concurrentes, Map ejecuta un sub-workflow por elemento de un dataset, y Fail/Succeed cierran la ejecución. Cada ejecución mantiene su historial visible para auditar, lo que elimina el «código pegamento» de reintentos, timeouts y manejo de errores que tú escribirías con Lambda.

Al crear la máquina de estados eliges un tipo inmutable. Los Standard Workflows son durable: duran hasta un año, ejecutan cada paso exactly-once (ideales para acciones no idempotentes como cobrar o lanzar un clúster EMR) y se facturan por state transition. Los Express Workflows duran hasta 5 minutos, cuestan mucho menos (por ejecución + duración + memoria) y ofrecen at-least-once (asíncronos) o at-most-once (síncronos): son la respuesta para ingesta masiva de IoT y streaming, donde las acciones son idempotentes y el volumen es alto.

Amazon MQ: cuando el broker ya existe

Hay sistemas que ya hablan el idioma de un message broker clásico con protocolos como JMS, AMQP, MQTT, OpenWire o STOMP. Amazon MQ administra brokers de Apache ActiveMQ y RabbitMQ (instalación, parches, versiones, HA active/standby) para migrar esas aplicaciones sin reescribir el código de mensajería. A diferencia de SQS/SNS, no es serverless: aprovisionas brokers (con costo por hora) y existe en la tabla mental como «el servicio para legacy». La recomendación oficial es clara: SQS y SNS para aplicaciones nuevas; Amazon MQ para migrar brokers existentes que exigen esos protocolos o APIs estándar.

6Amazon API Gateway y AWS AppSync

Amazon API Gateway es la «puerta frontal» serverless para crear, publicar y operar APIs REST, HTTP y WebSocket a cualquier escala: cientos de miles de llamadas concurrentes con gestión de tráfico, autorización, monitoreo (CloudWatch, X-Ray) y versionado. En una API REST modelas recursos y métodos (GET/POST sobre rutas jerárquicas), y para exponerla debes desplegarla en un stage (como /prod, /dev) mediante un deployment — cada deploy congela una instantánea de la API en ese stage. Los canary releases permiten desplegar gradualmente. Como es la frontera con internet, aquí viven las funciones de protección: autorizadores, throttling, caching y AWS WAF.

El primer examen interno es REST vs HTTP API. Ambos son RESTful; las REST APIs (v1) tienen más funciones y cuestan más; las HTTP APIs (v2) recortan funciones para costar menos. La tabla oficial de decisión: elige REST si necesitas API keys, throttling por cliente, request validation, AWS WAF, endpoints private o edge-optimized; elige HTTP si no necesitas nada de eso.

Autorizadores, planes y caching

Para quién puede llamar, API Gateway soporta IAM (firma SigV4, típico interno), Amazon Cognito user pools (el cliente trae un JWT que API Gateway valida), Lambda authorizers (una función tuya decide con lógica arbitraria — el antiguo «custom authorizer») y en HTTP APIs el JWT authorizer nativo (Cognito u otro OIDC). Para el cuánto puede llamar cada cliente: los usage plans asocian API keys a stages/métodos con throttling limits (rate = solicitudes/seg sostenidas; burst = capacidad instantánea) y quotas por período. Cuidado con dos matices: las API keys identifican al cliente pero no autentican (la doc oficial lo subraya), y los límites de usage plan son best-effort. El caching de respuestas se activa por stage: API Gateway guarda respuestas TTL configurable (por defecto 300 s, máximo 3600 s), reduce llamadas al backend y se cobra por hora según tamaño.

Las integraciones conectan cada método con el backend: Lambda proxy (la más común: toda la request en JSON a una función), AWS service (llamar una API de AWS directamente, p. ej. DynamoDB), HTTP (backend externo) y Mock (respuestas de prueba sin backend). Para APIs GraphQL el servicio es AWS AppSync: un endpoint GraphQL serverless que consulta múltiples data sources (DynamoDB, Lambda, HTTP…) mediante resolvers, mantiene subscriptions en tiempo real sobre WebSockets y ofrece caching y control de datos fino — la respuesta cuando el enunciado menciona GraphQL o actualizaciones real-time en apps móviles.

Señales del examen

"throttle requests per client" o "API keys" → REST API con usage plan (no HTTP API). "protect against common web exploits" → AWS WAF (REST, o CloudFront si es HTTP API). "reduce latency / backend calls" → enable caching con TTL. "GraphQL" o "real-time subscriptions" → AppSync. Y nunca elijas «API key para autenticar»: esa opción es un distractor documentado.

7Mapa final: patrón → servicio

Antes del examen, comprime toda la página en una sola tabla de decisión. Cuando leas el escenario, identifica el patrón de comunicación que pide y aplica la fila correspondiente; casi todas las preguntas de integración de D2 se resuelven con este filtro más el calificador de la pregunta. Practica recitándola: «poll → SQS, push a muchos → SNS, evento de AWS/SaaS con reglas → EventBridge, proceso de pasos → Step Functions, puerta HTTP → API Gateway, GraphQL real-time → AppSync, broker legacy → MQ».

Los 4 reflejos finales

1) Poll vs push: SQS el consumidor hace pull; SNS/EventBridge hacen push — si la pregunta dice «consumers poll messages», es SQS. 2) FIFO: la garantía exacta es exactly-once processing (procesado), no delivery. 3) Spikes: tráfico repentino que no debe perderse → SQS como buffer delante del worker. 4) Overhead: si hay que codificar reintentos, orden y errores entre Lambdas, la respuesta administrada es Step Functions, no más código.
