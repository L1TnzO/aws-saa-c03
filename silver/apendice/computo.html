Cómputo: Amazon EC2 y la familia de servidoresApéndice

El cómputo es el corazón del SAA-C03: casi la mitad de las preguntas terminan eligiendo dónde ejecutar una carga de trabajo. Esta página cubre Amazon EC2 a fondo (anatomía, familias, instance metadata, AMIs, hibernación), las opciones de compra y los servicios administrados que compiten con EC2: AWS Lambda, AWS Batch, Elastic Beanstalk, Outposts y Wavelength.

1Panorama de la familia de cómputo

AWS ofrece un espectro continuo de opciones de cómputo que van del máximo control al máximo despreocupamiento. En un extremo, Amazon EC2 te da una instance (servidor virtual) donde eliges sistema operativo, tamaño, red y parches. En el otro extremo, AWS Lambda ejecuta tu código sin que exista ningún servidor visible. En medio quedan los contenedores (ECS, EKS, Fargate), los trabajos por lotes (AWS Batch) y las plataformas gestionadas (Elastic Beanstalk). El examen no pregunta "¿qué es EC2?", sino "dada esta carga y estos requisitos, ¿cuál es la opción correcta?".

La regla mental es simple: más control implica más operación. Si eliges EC2, tú respondes por el sistema operativo, el escalado y las parchadas; si eliges Lambda o Fargate, AWS se encarga de la infraestructura y tú solo pagas por uso. Por eso el calificador del examen es tu brújula: least operational overhead empuja hacia la derecha del espectro (Lambda, Fargate), mientras que requisitos como long-running, acceso al SO o software legado empujan hacia EC2.

Señales del examen

Si la pregunta dice run continuously for hours, full administrative access o custom OS / legacy software, la respuesta casi siempre es EC2. Si dice event-driven, short tasks o no servers to manage, piensa en Lambda o Fargate antes que en EC2.

2Amazon EC2 a fondo

Amazon EC2 (Elastic Compute Cloud) provee capacidad de cómputo escalable bajo demanda: lanzas tantos servidores virtuales como necesites, en segundos, y pagas por lo que usas. Una instance es el servidor virtual; su instance type determina la combinación de CPU, memoria, red y almacenamiento que recibes. Las piezas básicas que el examen espera que domines son la AMI (la plantilla de software), el EBS root volume (el disco del sistema, persistente tras un stop), los security groups (el firewall virtual stateful de la instancia) y los key pairs (las credenciales para login por SSH o RDP).

Familias de instancias: qué letra, qué músculo

El nombre de un instance type (por ejemplo c7g.xlarge) codifica la familia, la generación y el tamaño. La letra inicial es lo importante para el examen porque resume el caso de uso típico: una r para hambre de memoria, una i para hambre de disco. Los tamaños van de nano a metal, y la generación alta suele traer mejores procesadores (los g finales — como en t4g o c7g — indican chips Graviton basados en Arm, más baratos que x86).

Instance Metadata Service v2 (IMDSv2) y la mitigación de SSRF

Cada instancia expone sus propios datos (su instance metadata: ID, tipo, rol IAM, dirección IP) en la dirección link-local 169.254.169.254, accesible solo desde dentro de la propia instancia. La versión 1 (IMDSv1) respondía a un simple GET, y eso la hacía vulnerable a ataques SSRF (Server-Side Request Forgery): si un atacante lograba que tu aplicación web hiciera una petición a esa IP, podía robar las credenciales temporales del rol IAM de la instancia. IMDSv2 cierra esa puerta exigiendo un flujo de dos pasos, orientado a sesión: primero un PUT para obtener un token con TTL y después el GET de metadata ya con ese token.

Error común

La metadata no está cifrada ni autenticada: cualquiera con acceso a la instancia puede leerla. Nunca guardes contraseñas ni secretos en el user data de lanzamiento, y fuerza IMDSv2 (con hop limit 1) para mitigar SSRF desde contenedores o apps web.

AMIs: tu propia, de Marketplace o de la comunidad

Una AMI (Amazon Machine Image) empaqueta el sistema operativo, el software y el block device mapping con el que arranca una instancia. Las AMIs son regionales: pertenecen a una Región concreta, aunque puedes copiarlas a otra Región o compartirlas con otras cuentas. Para el examen hay tres orígenes que debes distinguir porque cambian el costo y el control: crear la tuya propia (desde una instancia configurada o con EC2 Image Builder), comprarla en AWS Marketplace, o usar una pública/comunitaria. Las AMIs de la propia AWS (por ejemplo, Amazon Linux 2023) son el punto de partida habitual.

Origen de la AMIQuién la mantieneCuándo la elige el examen

AWS MarketplaceVendedor externo (pago por uso o por hora)Software comercial ya certificado (firewalls, ERPs) sin negociar licencias

Hibernación: stop vs stop-hibernate vs terminate

Una instancia puede pausarse de dos maneras. Con stop el sistema operativo se apaga: el EBS root volume sobrevive, pero la RAM se pierde y el arranque vuelve a arrancar de cero. Con stop-hibernate (hibernación) EC2 ordena al SO volcar la RAM al EBS root volume (suspend-to-disk): al reiniciar, se recarga la memoria y los procesos continúan donde estaban, con el mismo instance ID. Requiere habilitarla al lanzar la instancia, volumen raíz EBS cifrado, RAM soportada y tipos de instancia compatibles; no se paga por la instancia detenida, pero sí por el almacenamiento EBS (incluido el que ocupa la RAM). terminate destruye la instancia y, por defecto, el volumen raíz asociado.

AcciónRAMEBS root volumeInstance storeFacturación
stopSe pierdePersisteSe pierdeSin cargo de instancia; sí se paga el EBS
stop-hibernateVolcada al EBS rootPersiste (con la RAM dentro)Se pierdeSin cargo de instancia; se paga EBS ampliado
terminateSe pierdeSe borra por defecto (delete on termination)Se pierdeTodo desaparece

Fuente: bronze/05-docs/compute-ec2/hibernate.md.

Tip de estudio

La hibernación es la respuesta cuando la pregunta menciona una app que tarda mucho en bootstrap (calentar memoria, caches) y quieres pre-warm la instancia o pausar sin perder estado. Si en cambio la pregunta quiere ahorrar en instancias detenidas por largo tiempo, recuerda: igual pagas el EBS.

3Purchasing options: cómo pagar tus instancias

El mismo servidor EC2 puede costar muy distinto según cómo lo compres, y el examen (sobre todo en el dominio cost-optimized) te hará elegir el modelo correcto en una frase. Las cuatro opciones básicas son On-Demand (pago por segundo, sin compromiso), Spot (capacidad sobrante con hasta 90% de descuento a cambio de interrupciones con 2 minutos de aviso), Reserved Instances (compromiso de 1 o 3 años sobre una configuración concreta) y Savings Plans (compromiso de gasto por hora en USD, más flexible). A ellas se suman Dedicated Hosts (servidor físico completo para licencias o compliance) y Capacity Reservations (reservar capacidad en una AZ específica sin compromiso de descuento).

OpciónDescuento típicoCompromisoCuándo la elige el examen
On-Demand—Ninguno; pago por segundo (mín. 60 s)Cargas impredecibles, pruebas, apps que no pueden interrumpirse
SpotHasta ~90%Ninguno; puede interrumpirse con aviso de 2 minCargas tolerantes a fallos: batch, CI/CD, rendering, workers de cola
Reserved InstancesHasta ~72%1 o 3 años sobre instancia+Región (Standard o Convertible)Uso estable y previsible 24/7: bases de datos, ERPs
Savings PlansHasta ~66-72%1 o 3 años sobre USD/hora (Compute o EC2 Instance)Uso flexible: Compute Savings Plans cubre EC2 + Fargate + Lambda

Fuente: bronze/04-faqs/amazon-ec2.md (Savings Plans: hasta 66% en Compute, 72% en EC2 Instance).

Señales del examen

fault-tolerant batch workload, MOST cost-effective → Spot. steady state, 3-year commitment → Reserved/Savings Plans. cannot be interrupted → On-Demand o Reserved. El análisis costo-beneficio completo (incluyendo cómo combinar estos modelos con Auto Scaling) está en Dominio 4 · Cost-optimized.

4AWS Lambda a fondo

AWS Lambda es el cómputo serverless por excelencia: subes tu código (una function), eliges un runtime (Python, Node.js, Java, .NET, Ruby o uno propio) y AWS lo ejecuta automáticamente cuando ocurre un evento. No hay servidores que aprovisionar, parchear ni escalar: Lambda crea un execution environment aislado por cada solicitud concurrente y lo escala horizontalmente sin que toques nada. Pagas por el número de invocaciones y por la duración, medida en GB-seconds (memoria configurada × tiempo). Es la respuesta por defecto cuando el requisito es minimal operational overhead y la carga es event-driven.

Modos de invocación

La forma en que Lambda recibe el evento define quién espera la respuesta. En la invocación synchronous el cliente bloquea hasta recibir el resultado: es el caso de API Gateway, ALB o el SDK. En la asynchronous Lambda encola el evento, responde inmediatamente y reintenta solo ante errores (2 reintentos por defecto, con destinations o DLQ para capturar fallos): es el caso de S3 o SNS disparando funciones. En el modo stream / queue-based es Lambda quien sondea (polls) la fuente mediante un event source mapping, recibiendo registros en lotes: Kinesis, DynamoDB Streams, SQS y MSK funcionan así.

ModoEjemplos de origenQuién esperaReintentos ante error
SíncronaAPI Gateway, ALB, SDK/CLI, Function URLEl cliente (bloquea)Manuales: el error vuelve al llamador
AsíncronaS3 (eventos), SNS, EventBridge, CloudWatchNadie: Lambda encolaAutomáticos (2) + destinations o DLQ
Stream / colaSQS, Kinesis, DynamoDB Streams, MQ, MSKNadie: Lambda sondeaGestionados por el event source mapping (hasta caducar en la cola)

Concurrency: reserved vs provisioned

La concurrency es el número de ejecuciones simultáneas; por defecto la cuenta tiene un límite de 1.000 por Región, compartido por todas las funciones. La reserved concurrency aparta un cupo para una función crítica: le garantiza capacidad y a la vez actúa como techo (si pones 20, la función nunca pasará de 20). La provisioned concurrency es distinta: inicializa y mantiene caliente un número fijo de entornos para eliminar los cold starts, y se paga aunque nadie invoque la función; se asigna a una versión+alias concreta y puede auto-escalar programándose. El examen distingue la primera (garantía/techo, gratis) de la segunda (pre-calentar, con costo).

MecanismoQué haceCostoPregunta típica
Reserved concurrencyReserva un cupo del límite de cuenta; actúa como máximoGratis"Asegurar que la función X siempre tenga capacidad" o "proteger a las demás de una función voraz"
Provisioned concurrencyMantiene N entornos inicializados y listosSe paga continuamente"Eliminar latencia de arranque en una API sensible" (junto a SnapStart)

Fuente: bronze/05-docs/serverless-lambda/lambda-concurrency.md y provisioned-concurrency.md.

Cold starts y SnapStart

Un cold start ocurre cuando ninguna instancia del entorno está disponible y Lambda debe crear una: descargar código, arrancar el runtime e inicializarlo antes de ejecutar el handler. Para Python o Node.js suele ser decenas de milisegundos; para Java con frameworks pesados puede llegar a varios segundos. Lambda SnapStart ataca ese problema tomando un snapshot cifrado (memoria + disco) del entorno ya inicializado cuando publicas una versión: las invocaciones siguientes resume desde esa imagen y arrancan en menos de un segundo, sin tocar el código. Nació para Java 11+ (hoy también .NET 8 y Python 3.12+) y es la respuesta del examen cuando la pregunta menciona JVM + latencia de arranque; si el requisito es aún más estricto (doble dígito de milisegundos), la respuesta es provisioned concurrency.

Layers, versiones y alias

Las layers son paquetes de dependencias o runtimes que varias funciones comparten: en lugar de empaquetar la misma librería en cada ZIP, la subes una vez como capa y la adjuntas (hasta 5 por función). Cada vez que publicas código obtienes una version inmutable con su propio ARN; $LATEST es la única puntera y mutable. Los alias son punteros con nombre a una versión concreta (por ejemplo prod → v42) y permiten un traffic shifting entre dos versiones para despliegues canary o blue/green. Los triggers y el provisioned concurrency se configuran sobre alias, no sobre versiones directas.

Sobre las environment variables: se leen en claro dentro del runtime pero viajan cifradas en reposo; con una customer managed key de KMS controlas la rotación y los permisos de quién puede actualizar la configuración. Y en cuanto al escalado, no existe nada que configurar: cada solicitud concurrente recibe su entorno, de modo que 1.000 peticiones simultáneas significan hasta 1.000 entornos en paralelo (escala horizontal pura), solo frenada por los límites de concurrencia de la cuenta.

Señales del examen

least operational overhead o no infrastructure to manage + carga corta → Lambda. Pero cuidado con las trampas: si la tarea dura más de 15 minutos, si necesita GPU o acceso al SO, o si la pregunta menciona container image pesada y controlada por ti, Lambda ya no vale. Java cold start → SnapStart; consistent latency → provisioned concurrency.

5Batch, Beanstalk y cómputo híbrido/edge

AWS Batch es el servicio gestionado para batch computing: planifica y ejecuta miles de trabajos en contenedores sin que instales ni un planificador. Tú defines job definitions (imagen Docker, vCPU y memoria), las envías a job queues con prioridad, y los compute environments (EC2 On-Demand/Spot gestionados o Fargate) provisionan la capacidad según la demanda. Internamente Batch se apoya en la orquestación de contenedores de ECS y EKS, pero tú solo ves colas y trabajos. Es la respuesta del examen para large-scale batch workloads — rendering, simulaciones, ETL masivo — cuando gestionar EC2 a mano sería absurdo.

AWS Elastic Beanstalk es la capa platform as a service: subes tu código (Go, Java, .NET, Node.js, PHP, Python, Ruby o Docker) y Beanstalk provisiona y opera por debajo los EC2, el balanceador, el Auto Scaling y la monitorización con buenas prácticas. No cobra extra: pagas solo los recursos subyacentes, y con managed platform updates las parchadas son automáticas. Además de entornos web server, ofrece entornos worker que consumen de una cola SQS para tareas asíncronas. Lo que el examen pregunta una y otra vez son sus políticas de despliegue.

Finalmente, hay cargas que no pueden subir a la nube o que necesitan estar pegadas al usuario: ahí entran AWS Outposts y AWS Wavelength. Outposts instala hardware diseñado por AWS dentro de tu datacenter, para correr cómputo, almacenamiento y bases de datos con las mismas APIs y la misma consola, gestionado como parte de tu Región de AWS (racks o servidores 1U/2U). Wavelength extiende la VPC hasta el borde de las redes 5G de los operadores para dar latencias de un dígito de milisegundos a dispositivos móviles. Junto con Local Zones (centros de datos urbanos de baja latencia), completan el mapa híbrido/edge que el examen menciona con las frases data residency y ultra-low latency.

Señales del examen

"Ejecutar cargas en tu propio datacenter con los mismos servicios y APIs de AWS" → Outposts. "Latencia mínima para usuarios 5G" → Wavelength. "Colas de trabajos masivos sin gestionar infraestructura" → Batch. Y con Beanstalk, cuidado: si la pregunta exige full control of the underlying EC2, ya no es Beanstalk; si exige just upload the code, sí lo es.

Antes del examen convierte toda esta página en una tabla de reflejos. Cuando leas el escenario, localiza el criterio dominante (control, overhead, duración, costo, latencia) y salta directamente al servicio asociado.
