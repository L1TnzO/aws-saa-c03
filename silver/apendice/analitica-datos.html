Analítica y big dataD3 · data solutions

Del evento en vivo al dashboard: ingesta con Kinesis, lago en S3, transformación con Glue, cómputo con EMR y consumo con Athena, Redshift, QuickSight y OpenSearch. Esta página es el mapa completo de data ingestion and transformation que examina el Dominio 3.

Task Statement oficial 3.5
Determine high-performing data ingestion and transformation solutions
Knowledge: data analytics and visualization services (Amazon Athena, AWS Lake Formation, Amazon Quick), data ingestion patterns, data transformation services (AWS Glue), streaming data services (Amazon Kinesis) · Skills: building and securing data lakes, designing data streaming architectures, implementing visualization strategies, selecting compute for data processing (EMR), transforming data between formats (csv a parquet)

1El stack analítico de AWS

Una arquitectura analítica madura se lee de izquierda a derecha como una cadena de valor. Las fuentes (aplicaciones, logs, IoT, clickstream, bases de datos operacionales) generan datos continuamente. La ingesta los mueve a AWS: en tiempo real con Kinesis, por lotes con jobs de Glue o transferencias puntuales. El data lake central es S3 — barato, durable e ilimitado — con capas típicas raw (datos como llegaron) y curated (limpios, particionados, en parquet). El procesamiento transforma y enriquece (Glue, EMR), y el consumo lo pone frente a humanos: Athena para SQL ad-hoc, Redshift para BI intensivo, QuickSight para dashboards.

El examen casi nunca pregunta un servicio aislado: te da un punto de la cadena y te pide el siguiente con el calificador de siempre — least operational overhead empuja a lo serverless (Kinesis, Glue, Athena, Redshift Serverless); most cost-effective te lleva a particiones y parquet; real-time te manda directo a Kinesis. Ten este pipeline en la cabeza y cada pregunta de datos se vuelve «¿qué eslabón me están señalando?».

Tip de estudio

Aprende la cadena por velocidad: datos que no pueden esperar → Kinesis (segundos); datos que llegan en lotes → Glue; datos que ya están en S3 y quieres preguntarles → Athena. La velocidad de negocio del enunciado («real-time», «daily», «ad-hoc») decide el servicio.

2Amazon Kinesis: streaming en tiempo real

Kinesis es la familia de streaming de AWS. Kinesis Data Streams es el núcleo: un stream se divide en shards y cada shard ingiere 1 MB/s y sirve 2 MB/s de lectura. El productor envía cada registro con una partition key; Kinesis le aplica un hash y lo asigna a un shard, de modo que todos los registros con la misma clave van al mismo shard y conservan el orden. El retención es de 24 horas por defecto y puede extenderse hasta 365 días, lo que permite a un consumidor nuevo replay (releer el pasado). El retraso entre escribir y poder leer (put-to-get delay) es menor a un segundo.

Cada stream se dimensiona en modo provisioned (tú eliges el número de shards y pagas por ellos) o on-demand (escala automáticamente según el tráfico, ideal si este es impredecible). Para consumir hay dos modelos: los consumidores shared clásicos (todos comparten los 2 MB/s por shard, se reparten las particiones vía KCL, el Kinesis Client Library) y el enhanced fan-out, donde cada consumidor registrado recibe sus propios 2 MB/s por shard con push — más throughput por consumidor y latencia menor, a cambio de costo adicional.

Amazon Data Firehose (antes Kinesis Data Firehose) es el camión de entrega: un servicio totalmente administrado que lee un stream (o recibe eventos directamente) y los entrega near-real-time a S3, Redshift (vía S3 + COPY), OpenSearch, Splunk, terceros o endpoints HTTP. No escribes consumidores: configuras buffering hints (tamaño MB / intervalo de 60–900 segundos) que acumulan datos antes de escribir, una transformación opcional con Lambda por registro y la conversión de formato a parquet/ORC antes de aterrizar en S3. Es la respuesta «entregar mi stream en S3/Redshift with the least operational overhead». Completan la familia Managed Service for Apache Flink (antes Kinesis Data Analytics: SQL y Flink sobre los streams) y Kinesis Video Streams (video de cámaras y analítica en vivo).

Señales del examen

"real-time", "sub-second" o "replay data" → Kinesis Data Streams, nunca SQS. "deliver to S3 with no infrastructure" → Firehose. ¿Varios consumidores cada uno a plena velocidad? enhanced fan-out. ¿Volumen impredecible y no quieres gestionar shards? on-demand mode. La trampa: usar SQS cuando el enunciado pide que varias aplicaciones consuman los mismos datos históricos.

3Amazon MSK: Kafka administrado

Apache Kafka es el estándar de facto del streaming open source, y Amazon MSK (Managed Streaming for Apache Kafka) lo opera por ti: crea y mantiene el control plane — clústeres, brokers por Availability Zone (mínimo un broker por AZ, despliegue típico en tres), parches y versiones — mientras tú sigues usando las APIs y el ecosistema de Kafka sin tocar el código. Los clústeres MSK Provisioned usan hoy controladores KRaft (el reemplazo moderno de ZooKeeper para metadatos, incluido sin costo extra), y MSK Serverless elimina incluso la gestión de capacidad. MSK Connect añade conectores de entrada/salida listos para usar. En el examen MSK aparece como la respuesta cuando el escenario ya habla Kafka explícitamente (equipos, tools o dependencias Kafka) o exige su ecosistema; para lo demás, Kinesis es más simple y está más integrado con los servicios AWS.

4Data lake: S3, Lake Formation y AWS Glue

El data lake es el patrón de almacenamiento central: todo tipo de datos (estructurados, semi, no) a costo de S3, sin esquema rígido de entrada. Pero un lago sin gobierno es un data swamp: nadie sabe qué hay ni quién puede verlo. AWS Lake Formation aporta el gobierno centralizado: sobre el Glue Data Catalog aplica un modelo de permisos propio con grants y revokes estilo RDBMS, con control fine-grained a nivel de columna, fila y celda, y lo comparte incluso entre cuentas. Los servicios analíticos (Athena, Redshift Spectrum, EMR, Glue) consultan el catálogo y respetan esos permisos. Recuerda la imagen mental: S3 guarda los datos, el Catálogo los describe, Lake Formation decide quién los ve.

AWS Glue es la navaja suiza de la integración: un servicio de ETL serverless con tres piezas que caen en examen. Primera, los crawlers: recorren tus datos en S3 (o bases de datos), infieren el esquema y crean/actualizan tablas en el Data Catalog — el inventario técnico central de tus datos. Segunda, los ETL jobs: transformaciones Spark que se ejecutan sin que administres clústeres, con job bookmarks que recuerdan lo ya procesado para no duplicar trabajo incremental, triggers (por schedule, evento o demanda) y autogeneración de código desde Glue Studio (el editor visual); hay también jobs Python Shell ligeros. Tercera, las herramientas de preparación: AWS Glue DataBrew permite a analistas limpiar y preparar datos con recetas visuales sin escribir código. Cuando el enunciado dice "serverless ETL" o "convert CSV to parquet", la respuesta es Glue.

5Amazon EMR: big data con clústeres

Amazon EMR (ex Elastic MapReduce) es la plataforma administrada de clústeres para frameworks de big data: Spark (el caballo de batalla), Hadoop, Hive, Pig, Presto/Trino y HBase, con datos que suelen vivir en S3. Un clúster EMR tiene tres tipos de nodo con roles distintos: el master node coordina y ejecuta el gestor de recursos (YARN); los core nodes almacenan datos en HDFS y computan; y los task nodes solo computan — al no llevar datos, son perfectos para Spot Instances que puedes perder sin corromper el clúster. Para elegir instancias hay instance groups (tipos fijos por rol) o instance fleets (mezcla de tipos y de On-Demand + Spot con objetivos de capacidad), y On-Demand/Reserved para lo crítico con Spot para lo interrumpible.

El costo-optimización clásico de examen: task nodes con Spot para absorber picos de cómputo barato, master/core en On-Demand. Y el comodín moderno es EMR Serverless: ejecutas jobs de Spark y Hive sin crear ni gestionar clúster — paga por uso, cero operación. La dicotomía que debes recitar: si el escenario pide ETL administrado sin fricción → Glue; si exige control del runtime, trabajos custom, ML pesado o frameworks específicos → EMR (Serverless si además pide least overhead).

Señales del examen

"run Spark jobs without managing clusters" → EMR Serverless (o Glue si es ETL de catálogo). "cost-effective batch" con interrupciones tolerables → task nodes en Spot. "existing Hive/Pig/Spark workload on EC2" → migrar a EMR, no reescribir. Y recuerda: salida y entrada grandes viven en S3, no en HDFS del clúster efímero.

6Consulta y BI: Athena, Redshift, QuickSight y OpenSearch

Amazon Athena es SQL serverless sobre S3 (motor Presto/Trino): apuntas a los datos y consultas, sin infraestructura, pagando por TB escaneados. Ese precio por escaneo es la palanca de diseño: con formato columnar parquet, compresión y particiones (partitioning), Athena lee solo las columnas y particiones que la query necesita (partition pruning) y el costo cae órdenes de magnitud frente a CSV plano. Los workgroups agrupan y controlan queries por equipo (límites y destinos de resultados), y los federated queries extienden el SQL a otras fuentes (RDS, DynamoDB…) vía conectores Lambda, usando el Glue Data Catalog como metastore.

Amazon Redshift es el data warehouse columnar para BI pesado: un clúster con leader node que planifica y compute nodes que ejecutan. Con nodos RA3 el almacenamiento es managed storage desacoplado del cómputo (los bloques fríos van a S3). Sus tres trucos de examen: Redshift Spectrum consulta datos directamente en S3 con tablas externas — sin cargarlos al clúster —; Concurrency Scaling añade clústeres transitorios para picos de queries concurrentes; y Redshift Serverless elimina el clúster y factura por unidades de procesamiento (RPU) — la opción cuando el patrón de uso es intermitente.

Amazon QuickSight (hoy parte de la suite Amazon Quick) es el BI serverless de AWS: dashboards con SPICE — su motor in-memory Super-fast Parallel In-memory Calculation Engine que cachea datasets para responder al instante — además de ML Insights (detección de anomalías y forecasting automáticos) y paga por usuario/sesión. Finalmente Amazon OpenSearch Service opera clústeres del motor open source OpenSearch (dominios con instancias que eliges): es la respuesta para búsqueda full-text, analítica de logs y monitoring en tiempo real, con OpenSearch Dashboards para visualizar y capas UltraWarm/cold para datos de solo lectura.

Señales del examen

"query data in S3 without infrastructure" → Athena. "reduce Athena cost" → parquet + compresión + particiones. Un warehouse con reporting diario y joins pesados → Redshift; si además aparece S3 enorme sin cargar → Spectrum. "dashboards" → QuickSight con SPICE. "search logs / full-text" → OpenSearch. La trampa: elegir Redshift cuando todo está en S3 y basta SQL puntual.

7Caso integrador: el lago de punta a punta

Junta todo en un diseño real de examen. Una aplicación web emite eventos de interacción; Kinesis Data Streams los ingiere en segundos (partition key = user id, shards en modo on-demand para absorber picos). Cada evento viaja de dos formas: un consumidor en vivo calcula métricas inmediatas, y un Data Firehose aplica una transformación Lambda que limpia y valida registros, convierte a parquet y aterriza en S3 con layout particionado: s3://lake/events/year=2025/month=09/day=11/. Un crawler de Glue actualiza el Data Catalog con las nuevas particiones, y los permisos finos por columna los define Lake Formation. Los analistas lanzan Athena con WHERE year='2025' AND month='09': el partition pruning hace que solo se escaneen esos prefijos — y como parquet es columnar, solo las columnas del SELECT. El resultado: queries de segundos y facturas mínimas por TB escaneado. QuickSight sirve dashboards sobre SPICE para dirección; un job semanal de Glue consolida el histórico para el equipo de ML.

Tu tabla de decisión final para cualquier pregunta de datos en el SAA-C03.

Los 5 reflejos finales

1) «SQL serverless sobre S3» = Athena. 2) «ETL administrado / transformar formatos» = Glue. 3) «ML / frameworks / control del cómputo sobre datasets enormes» = EMR (o SageMaker si el foco es entrenar modelos). 4) «real-time / streaming» = Kinesis. 5) Reducir costo de Athena = columnar + compressed + partitioned: si una opción ofrece parquet particionado, es casi siempre la correcta.
