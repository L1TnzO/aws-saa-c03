Redes y conectividad: VPC y más alláD2 · D3

Redes es el área más densa del examen: casi ninguna pregunta escapa a una VPC, un subnet o una decisión de conectividad. Esta página recorre todo el mapa — de la VPC regional al edge global — con las tablas de decisión que el examen te va a pedir.

Task Statement oficial 2.1
Design high-performing and/or efficient networking solutions
Knowledge: connectivity to AWS, DNS, network performance · Skills: Route 53, CloudFront, Global Accelerator, VPC endpoints, hybrid connectivity (VPN / Direct Connect / Transit Gateway)

1El mapa mental de redes AWS

Antes de memorizar servicios, necesitas un mapa: las redes de AWS se organizan en capas concéntricas y cada pregunta del examen vive en una capa concreta. La capa regional contiene tus VPCs con sus subnets y route tables. Dentro de cada VPC decides cómo salir a internet (internet gateway, NAT gateway), cómo llegar a servicios AWS sin internet (VPC endpoints) y cómo distribuir carga (load balancers). Hacia afuera están la capa híbrida (VPN, Direct Connect, Transit Gateway) y la capa global (Route 53, CloudFront, Global Accelerator).

Este orden no es casual: es exactamente el orden en que se diseña una arquitectura. Primero defines el espacio de direcciones (CIDR), luego segmentas por Availability Zone y función, luego el enrutamiento, y solo al final añades conectividad externa. Si una pregunta menciona dos servicios de capas distintas, casi siempre preguntan por el límite entre ellas — por ejemplo, cómo llega tráfico de un usuario global hasta una instancia en una subnet privada.

CapaPregunta clave del diseñoServicios protagonistas

Routing¿Por dónde sale cada paquete?Route tables, IGW, NAT gateway

Conectividad privada a AWS¿Cómo llego a S3 o a un SaaS sin internet?VPC endpoints, PrivateLink

Fuente: documentación oficial (bronze · network-vpc, network-tgw y demás guías).

Tip de estudio

Cuando leas una pregunta de redes, ubica primero la capa: si el escenario habla de "users connecting from anywhere", es capa híbrida (Client VPN); si habla de "global audience" y latency, es capa edge. La capa te elimina la mitad de las opciones al instante.

2Amazon VPC a fondo: CIDR, subnets y routing

Amazon VPC (Virtual Private Cloud) es tu red privada y lógicamente aislada dentro de una región de AWS. Cada VPC se define con un bloque CIDR (Classless Inter-Domain Routing): una dirección IP más una máscara, como 10.0.0.0/16, que representa 65.536 direcciones. En la práctica casi todos los rangos de VPC caen dentro de los espacios privados del estándar RFC 1918, que no son enrutables desde internet — exactamente lo que quieres para una red interna. Recuerda el detalle de cobro moderno: AWS cobra hoy todas las IPs públicas IPv4 (incluidas las Elastic IP sin uso), mientras que las privadas de RFC 1918 son gratis.

2.1 El tamaño de las subnets y las 5 IPs reservadas

Una subnet es una porción del CIDR de la VPC y vive siempre en una sola Availability Zone — nunca cruza AZs. El tamaño permitido para una subnet IPv4 va de /16 (65.536 direcciones) hasta /28 (16 direcciones), el mínimo. En cada subnet AWS reserva 5 direcciones que no puedes usar: la dirección de red (x.x.x.0), la del VPC router (.1), la del servidor Amazon DNS (.2), una para futuro (.3) y la de broadcast (.255, aunque el broadcast no se soporta en VPC). La consecuencia aritmética que adora el examen: una subnet /28 solo ofrece 11 IPs utilizables, y una /24 ofrece 251.

2.2 Public vs private: lo decide la route table

Que una subnet sea public o private no es un checkbox: lo determina su route table. Cada VPC nace con la main route table; toda subnet sin asociación explícita la hereda. Cada subnet se asocia a una sola route table a la vez, aunque una misma route table puede servir a muchas subnets. La regla práctica: subnet pública = tiene ruta 0.0.0.0/0 → igw hacia el internet gateway; subnet privada = no la tiene, y su salida a internet (si existe) pasa por un NAT gateway colocado en una subnet pública.

2.3 Los cuatro dispositivos de salida

El internet gateway es el canal bidireccional entre tu VPC e internet: se despliega con redundancia y disponibilidad por diseño, no tiene límite de ancho de banda y no se cobra. El NAT gateway es el servicio administrado que permite salida iniciada desde dentro en IPv4: los recursos de subnets privadas alcanzan internet pero nadie puede iniciar conexión hacia ellos. La NAT instance es su ancestro: un EC2 tú mismo configurado como router NAT. Por último, el egress-only internet gateway hace el papel de NAT pero para IPv6: permite la salida iniciada desde dentro y bloquea toda entrada no solicitada, de forma stateful.

El patrón canónico del examen es la VPC multi-AZ de 3 capas: el balanceador en subnets públicas de dos AZs, la aplicación en subnets privadas y la base de datos en subnets privadas sin ruta de salida. Para que las instancias privadas actualicen software o llamen APIs externas, cada AZ lleva su NAT gateway en su subnet pública — un NAT por AZ evita el tráfico cross-AZ, que se cobra. El IGW único atiende toda la VPC.

Señales del examen

"Resources in private subnets need to download patches from the internet" → NAT gateway (no "assign public IPs" ni NAT instance si el calificador es least operational overhead). "IPv6 egress only" → egress-only internet gateway, nunca NAT gateway. Y ojo: la default VPC existe en cada región con subnets públicas — varios escenarios parten de ella.

Error común

Asociar subnets de distintas AZs a rutas que atraviesan el NAT de otra AZ: funciona, pero el cross-AZ traffic se cobra en ambas direcciones. La respuesta "correcta" en preguntas de costo incluye un NAT gateway por AZ o, mejor aún, un gateway endpoint si el destino es S3 o DynamoDB.

3Seguridad de capa 4: dos muros y un registrador

La seguridad de red clásica en AWS vive en capa 4: IP y puerto. Tiene dos muros complementarios — el security group (SG) y la network ACL (NACL) — y un registrador de todo lo que pasa: los VPC Flow Logs. El SG es un firewall stateful que se asocia a network interfaces (a la instancia, en la práctica); la NACL es stateless y se asocia a la subnet completa, evaluando reglas numeradas en orden. El detalle que aparece una y otra vez: el SG solo tiene reglas allow (todo lo no permitido está negado, y las respuestas de conexiones permitidas vuelven solas gracias a su estado), mientras que la NACL tiene allow y deny explícitos y necesitas abrir también el tráfico de retorno. La profundidad completa de este tema está en D1 · Secure Architectures; aquí basta la tabla de decisión rápida.

Estadostateful: las respuestas pasan solasstateless: hay que abrir ida y vuelta
ReglasSolo allow; se evalúan todasAllow y deny; se evalúan por número, de menor a mayor
Return trafficAutomáticoManual (regla ephemeral 1024-65535)
Uso típicoFiltro por defecto para todoBloquear IPs maliciosas explícitamente, capa de defensa extra

Fuente: ../../bronze/05-docs/network-vpc/vpc-security-groups.md y vpc-network-acls.md.

Los VPC Flow Logs capturan metadatos del tráfico IP que entra y sale de las interfaces de red: quién habló con quién, en qué puerto y si la conexión fue ACCEPT o REJECT. Se pueden crear a nivel de VPC, subnet o ENI, y el tipo de captura es all (todo), accept o reject. Tienen tres destinos posibles: Amazon S3, CloudWatch Logs y Amazon Data Firehose (KDF) para llevarlo a analítica externa. Como se recolectan fuera del camino del tráfico, no afectan latencia ni throughput — dato que el examen menciona como ventaja frente a un IDS casero. No son tiempo real: son evidencia a posteriori.

Señales del examen

"Troubleshoot why traffic is not reaching an instance" o "audit connectivity between subnets" → VPC Flow Logs (a S3 o CloudWatch según pidan analítica o alarmas). "Block a specific IP address at the subnet level" → NACL, porque un SG no puede denegar IPs explícitamente. Recuerda también Reachability Analyzer para pruebas de conectividad puntual sin generar tráfico.

4Híbrido: VPN, Direct Connect y Transit Gateway

Cuando el escenario dice hybrid — un data center on-premises, oficinas o usuarios remotos — aparecen tres familias de servicios. La AWS Site-to-Site VPN conecta tu red corporativa con AWS por internet, cifrada con IPsec. Del lado tuyo defines el customer gateway (CGW, el recurso que describe tu dispositivo); del lado AWS el extremo es una virtual private gateway (VGW) asociada a una VPC, o mejor, un Transit Gateway. Cada conexión incluye dos túneles por alta disponibilidad, y el enrutamiento puede ser estático o dinámico con BGP — dinámico casi siempre que el examen lo ofrezca. La variante accelerated Site-to-Site VPN usa Global Accelerator para entrar por el edge más cercano y viajar por la red troncal de AWS; solo se soporta sobre Transit Gateway, no sobre VGW.

La AWS Client VPN resuelve el otro extremo híbrido: usuarios individuales, no redes. Es un servicio administrado basado en OpenVPN: creas un Client VPN endpoint, le asocias subnets de una o más VPCs (o un TGW), y los usuarios se autentican con Active Directory, federated authentication (SAML 2.0) o certificados mutuos. Las authorization rules controlan qué grupos de identidades acceden a qué redes, y el self-service portal deja que cada usuario descargue su cliente y configuración. La señal del examen es inequívoca: "users connect from anywhere to resources in the VPC" → Client VPN; "connect the entire on-premises network" → Site-to-Site.

AWS Direct Connect (DX) es la conexión física y dedicada entre tu infraestructura y AWS: se contrata en una DX location y viaja por fibra privada, no por internet, dando latencia consistente y ancho de banda garantizado. Las conexiones dedicated te reservan un puerto físico (1, 10, 100 o 400 Gbps), mientras que las hosted te vende capacidad sobre un puerto compartido de un Direct Connect Partner (desde 50 Mbps hasta 10 Gbps, e incluso 25 Gbps con partners concretos). Para resiliencia se usa el Direct Connect Resiliency Toolkit con modelos de 99.9% (High) y 99.99% (Maximum), y el patrón de examen por excelencia: DX como primario + Site-to-Site VPN como backup. Un LAG (agregación de enlaces) combina varias conexiones en una lógica, y MACsec añade cifrado de capa 2 en conexiones dedicadas de 10 Gbps o más en las locations que lo soportan.

¿Y cómo se une todo sin construir una malla? Con AWS Transit Gateway (TGW), el hub-and-spoke de AWS. Un TGW regional acepta attachments de VPCs, conexiones Site-to-Site VPN, Direct Connect gateways (mediante transit VIF) e incluso peering con otros TGWs — incluyendo inter-region peering que viaja cifrado (AES-256) por la red troncal global de AWS. Cada attachment se asocia a una TGW route table y puede propagar rutas dinámicamente (BGP desde VPN y DX; estáticas hacia las VPCs), lo que permite segmentar: por ejemplo, una tabla para producción y otra para dev, compartiendo el mismo DX. El contraste clásico con VPC peering: el peering es no transitivo y crece como n(n-1)/2; el TGW centraliza con un solo punto de gestión.

Señales del examen

"Connect 15 VPCs and an on-premises data center with minimal operational overhead" → Transit Gateway (no malla de peering). "Primary connection fails → traffic must fail over automatically" → DX + backup VPN con BGP/ failover. "Encrypt all traffic over Direct Connect at layer 2" → MACsec. Y la trampa favorita: "accelerated VPN" solo existe con TGW, no con VGW.

5VPC endpoints y PrivateLink: privado hasta el hueso

Hay dos formas de que una instancia en una subnet privada hable con S3: pagar el peaje del NAT o ir por el camino privado. Los VPC endpoints son ese camino: conectividad privada a servicios de AWS sin atravesar internet, sin IGW, sin NAT y sin IP pública. Vienen en dos familias muy distintas. El gateway endpoint existe solo para Amazon S3 y DynamoDB: se configura como una ruta especial en la route table (un prefix list apuntando al endpoint) y es gratuito. El interface endpoint usa AWS PrivateLink: crea una ENI con una IP privada de tu subnet, uno por AZ para resiliencia, y sí se cobra (hora por endpoint por AZ más GB procesados). Con private DNS activado, el nombre público del servicio (p. ej. s3.us-east-1.amazonaws.com) resuelve dentro de la VPC a la IP del endpoint, sin tocar una línea de código.

ServiciosSolo S3 y DynamoDBDecenas: SQS, KMS, CloudWatch, API Gateway, S3…
MecanismoRuta en la route table (prefix list)ENI con IP privada de tu subnet, vía PrivateLink
CostoGratisPor hora + por GB procesados
AlcanceSolo desde la VPC, misma regiónAccesible también vía VPN, DX y VPC peering/TGW
ResilienciaRegional, sin AZsAZ-resilient: endpoint por AZ + SG propio
Señal de examen"cost-effective access to S3 from private subnets""privately connect to any AWS service / on-prem"

Fuente: ../../bronze/05-docs/network-privatelink/gateway-endpoints.md y interface-endpoints.md.

AWS PrivateLink es la tecnología general que hay debajo y también el nombre del producto cuando el extremo no es un servicio AWS sino un servicio de terceros o de otra cuenta AWS: un SaaS expone su servicio tras un Network Load Balancer y publica un VPC endpoint service; tú consumes desde tu VPC con un interface endpoint. El tráfico nunca sale de la red de AWS y no hay solapamiento de CIDRs, a diferencia del peering. Es LA respuesta cuando el enunciado insiste en "private connectivity", "without traversing the internet" o "connect to a SaaS provider securely".

Señales del examen

"Reduce NAT gateway costs for S3 traffic" → gateway endpoint (gratis, regional). "Instances must access SQS/KMS without internet and with no code changes" → interface endpoint + private DNS. "Access a partner's application over private connectivity" → PrivateLink al endpoint service del partner. Trampa: el gateway endpoint no se puede usar desde otra VPC peered ni desde on-prem — para eso, interface endpoint.

6Route 53 a fondo: DNS global con política de enrutamiento

Amazon Route 53 (53 por el puerto de DNS) es un servicio DNS global con un SLA de disponibilidad del 100%. Sus registros viven en hosted zones: la public hosted zone define cómo resuelve el mundo exterior para tu dominio, y la private hosted zone lo hace solo dentro de tus VPCs asociadas — perfecta para resolver api.internal hacia IPs privadas. Además de DNS, Route 53 es un domain registrar: puedes registrar y transferir dominios desde la misma consola, lo que en el examen aparece como "register a domain with the least overhead". La pieza que convierte a Route 53 en herramienta de arquitectura es la combinación de routing policies + health checks.

Los health checks son sondas independientes que monitorizan un endpoint (IP o dominio, con path, puerto e intervalo configurables), un CloudWatch alarm, o incluso otros health checks — los calculated health checks, que combinan varios con lógica AND/OR para implementar quórum ("failover solo si fallan dos de tres regiones"). La variante string match considera sano al endpoint solo si el cuerpo de la respuesta HTTP contiene un texto concreto, ideal para detectar que la app sirve la página de error. Con alias records hacia ALBs, CloudFront distributions o buckets de sitio web, el evaluate target health hereda la salud del objetivo sin health check propio. Y para recuperación por encima de DNS existe AWS Application Recovery Controller (ARC), con routing controls y zonal shift para apartar el tráfico de una AZ dañada en segundos — la mención moderna en preguntas de recuperación.

Señales del examen

"Route users to the closest Region" → latency; "based on the user's country" → geolocation (¡no latency!). "Gradually shift traffic between regions based on resource location" → geoproximity con bias. "Automatically route to a standby if the primary is unhealthy" → failover + health check. Distingue siempre latency (récord: velocidad) de geolocation (regla: ubicación del usuario).

7Edge y global: CloudFront, Elastic IP y Global Accelerator

Amazon CloudFront es la CDN de AWS: una distribution define orígenes (origins) — un bucket S3, un ALB, un EC2 o cualquier servidor HTTP (custom origin) — y los cache behaviors deciden qué rutas se cachean, con qué TTL y a qué headers se hace caso. Las peticiones de tus usuarios entran por la edge location más cercana de una red de cientos de POPs y viajan hacia el origen por la red troncal de AWS; si el objeto está en caché (cache HIT) ni siquiera se toca el origen. El TTL por defecto es 24 horas, el mínimo 0 segundos y no hay máximo — el examen pregunta "¿cuánto vive un objeto en la caché?" con esa respuesta. El price class limita qué POPs usas para bajar factura (solo NA+Europa, o NA+EU+regiones seleccionadas, o todo el mundo), y el Origin Shield añade una capa de caché intermedia que protege al origen de ráfagas.

Para contenido privado, CloudFront ofrece dos mecanismos: las signed URLs y las signed cookies, firmadas por trusted key groups. Y para que nadie rodee CloudFront hacia un bucket S3, se usa Origin Access Control (OAC, el sucesor del viejo OAI): el bucket queda privado y solo la distribución autorizada lee de él. La personalización en el edge se escribe con dos runtimes: las CloudFront Functions — ligeras, submilisegundo, solo eventos de viewer — y Lambda@Edge — funciones Lambda completas que también interceptan eventos de origin.

Fuera del mundo HTTP quedan dos piezas finales. La Elastic IP (EIP) es una IPv4 pública estática de tu propiedad que asocias y desasocias de recursos a voluntad — pero hoy se cobra si no está asociada a un recurso en uso, así que "reservar EIPs por si acaso" ya no es la respuesta correcta; y con BYOIP puedes traer tus propios rangos públicos a AWS. El AWS Global Accelerator (GA) usa anycast: te da dos IP estáticas que se anuncian desde todos los edges del mundo; el usuario entra por la más cercana y su tráfico viaja por la red global de AWS hasta un endpoint (ALB, NLB, EC2 o EIP) en la región que elijas. Con traffic dials ajustas el porcentaje de tráfico por grupo de endpoints, y el failover basado en salud es instantáneo — también respeta los zonal shifts de ARC. Cuando el examen dice "static IPs + TCP/UDP global + no HTTP", la respuesta es GA, no CloudFront.

Tips transversales de redes

1) "Private connectivity" casi siempre significa PrivateLink / VPC endpoint — no VPN. 2) El tráfico cross-AZ se cobra: coloca recursos redundantes en la misma AZ cuando la pregunta hable de data transfer cost, y multi-AZ cuando hable de high availability. 3) "Edge + low latency" = CloudFront; añade "static IP" o protocolos no HTTP = Global Accelerator. 4) La subnet vive en una sola AZ y una subnet usa una sola route table a la vez. 5) Los CIDRs de VPCs que se van a conectar (peering, TGW, VPN) no deben solaparse — distractor recurrente con el rango 172.31.0.0/16 de la default VPC.
