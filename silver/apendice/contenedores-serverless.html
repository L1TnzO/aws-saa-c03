Contenedores y serverlessApéndice

Contenedores y funciones son las dos formas modernas de empaquetar cómputo en AWS. Esta página cubre el ecosistema completo — Amazon ECS, Amazon EKS, Amazon ECR y AWS Fargate — junto con los serverless patterns (SQS, EventBridge, Step Functions) que el SAA-C03 usa para armar arquitecturas event-driven con el mínimo operational overhead.

1Por qué contenedores (y contra qué compiten)

Un contenedor empaqueta una aplicación con sus dependencias en una unidad ligera y portable: se construye una vez como image y corre idéntica en tu laptop, en ECS, en EKS o en Fargate. Esa portability elimina el clásico "en mi máquina sí funciona", porque el entorno viaja con el código. Además dan density: un mismo host ejecuta decenas de contenedores aislados, aprovechando mejor la CPU y la memoria que una máquina virtual por aplicación. Y al ser immutable, cada despliegue es una nueva imagen de la aplicación — auditable y con rollback trivial.

El stack AWS para contenedores tiene tres capas que conviene separar mentalmente: el registro donde viven las imágenes (Amazon ECR), los orquestadores que deciden dónde y cuántos contenedores corren (Amazon ECS propio, Amazon EKS basado en Kubernetes), y la capacidad sobre la que corren (instancias EC2 que tú gestionas, o el motor serverless AWS Fargate que las gestiona AWS). La pregunta de diseño del examen es casi siempre esa: ¿quién orquesta y quién opera los servidores?

Cuando el examen compara, casi siempre yuxtapone tres formas de empaquetar cómputo: la máquina virtual (EC2), el contenedor y la función. La tabla siguiente resume el espectro de gestión; memorízala porque en las preguntas de migración modernización aparece tal cual: rehost te deja en EC2, replatform te lleva a contenedores y refactor te acerca a funciones.

2Amazon ECS: el orquestador nativo de AWS

Amazon Elastic Container Service es el orquestador de contenedores propio de AWS, totalmente gestionado (sin control plane que operar ni pagar aparte). Su vocabulario es materia de examen: la task definition es el plano en JSON que describe cada contenedor — imagen de ECR, CPU y memoria requeridas, puertos, variables de entorno y el task IAM role con el que la tarea llama a otros servicios. Un task es una ejecución concreta de ese plano (uno o varios contenedores juntos). Un service mantiene vivo un número de tareas (desired count) reemplazando las que fallan, y el cluster es la agrupación lógica donde todo corre sobre una capacidad elegida.

La capacidad se elige por launch type o, mejor aún, con capacity providers: AWS recomienda definir en la task definition las compatibilidades de launch type y lanzar los servicios con una capacity provider strategy. Los providers pueden ser Fargate y FARGATE_SPOT (creados por AWS en todo cluster), grupos de Auto Scaling con instancias EC2 tuyas, o los nuevos ECS Managed Instances. Para escalar hay dos palancas distintas: el service auto scaling ajusta el número de tareas (por métrica de CPU, memoria o peticiones por target del ALB, con target tracking), mientras el cluster auto scaling escala las instancias EC2 de fondo cuando faltan recursos para colocar tareas.

Launch typeDónde corren las tareasTú gestionasCaso típico
EC2Instancias EC2 registradas al clusterEl SO, el parcheo, el tamaño y el escalado del clusterGPU, daemon sets, precios agresivos con Spot dedicado
FargateCapacidad serverless gestionada por AWSNada: solo vCPU y memoria por tareaWebs y APIs estándar con least overhead

Fuente: bronze/05-docs/containers-ecs/capacity-launch-type-comparison.md y welcome.md.

Tip de estudio

Memoriza la pareja de roles de ECS: el task role es lo que usa el contenedor para llamar a AWS (por ejemplo, escribir en S3), mientras el instance role (en launch type EC2) es lo que usa la instancia para llamadas de plataforma. El examen mezcla ambos a propósito.

3Amazon EKS: Kubernetes gestionado

Amazon Elastic Kubernetes Service corre Kubernetes real: AWS opera el control plane (API server, etcd, scheduler) por una tarifa horaria, y tú eliges quién gestiona los nodes del data plane. La gran ventaja es la compatibilidad con el ecosistema: si tu equipo ya escribe manifiestos YAML, usa Helm u operadores (operators), EKS es el camino natural — portability total de Kubernetes entre nubes e incluso on-premises con EKS Anywhere e Hybrid Nodes. La desventaja es el precio y la curva: es el orquestador con más superficie de decisión del examen.

Para el data plane hay tres caminos. Los managed node groups crean y parchean por ti los grupos de Auto Scaling de instancias (tú eliges tipo de instancia y Amazon Linux/EKS-optimized AMI); los nodos self-managed son instancias EC2 que tú registras y mantienes (útil para configuraciones especiales de OS o GPUs con drivers propios); y los Fargate profiles hacen que los pods de namespaces/labels concretos corran en capacidad Fargate sin ver un nodo. La opción más reciente, EKS Auto Mode, extiende la gestión a los nodos completos — aprovisiona, escala y parchea por ti. Los add-ons gestionados (VPC CNI, CoreDNS, kube-proxy) mantienen los componentes esenciales actualizados.

Fuente: bronze/05-docs/containers-eks/what-is-eks.md y managed-node-groups.md.

Señales del examen

EKS se elige por dos motivos y casi ninguno más: ya existe Kubernetes (equipo experto, manifiestos que migrar, operadores que usar) o se necesita vendor neutrality / portabilidad a otras nubes. Si la pregunta solo pide "correr contenedores en AWS de la forma más simple", EKS es la distractora cara y compleja: la respuesta es ECS o Fargate.

4Amazon ECR: el registro privado de imágenes

Amazon Elastic Container Registry es el registro gestionado donde viven tus imágenes Docker y artefactos OCI, con permisos por repositorio basados en IAM (resource-based policies que deciden qué usuarios o cuentas pueden hacer push/pull). Se integra directamente con ECS y EKS — de hecho su setup es una extensión de ambos — y cobra por almacenamiento, transferencia y acciones opcionales. Tres features aparecen en el examen: las lifecycle policies que limpian automáticamente imágenes viejas o sin tag (para no pagar storage infinito), el image scanning con scan on push que detecta vulnerabilidades al subir cada imagen, y la replication cross-Region/cross-account para tener las imágenes cerca de cada cluster. Complétalo con tag immutability (nadie sobrescribe un tag ya publicado) y el pull-through cache que sincroniza imágenes de registros upstream externos.

Error común

Confundir "Fargate" con un orquestador. Fargate no compite con ECS ni EKS: es la capa de capacidad para ECS y EKS. Primero eliges el orquestador (ECS vs EKS), luego la capacidad (EC2 vs Fargate). Una opción tipo "usar Fargate en vez de ECS" en el examen es casi siempre incorrecta.

5AWS Fargate: serverless para contenedores

AWS Fargate es el motor de cómputo serverless para contenedores: le dices a cada task cuántas vCPU y cuánta memoria necesita (configuraciones de 0,25 vCPU/0,5 GB hasta 16 vCPU/120 GB en ECS) y AWS provisiona, aísla y parchea la infraestructura por ti. No hay instancias que elegir, clusters que llenar ni hosts que actualizar — cada tarea corre en su propio entorno aislado de kernel (microVM), lo que también mejora el aislamiento de seguridad entre cargas. Se paga por lo que consumen las tareas: vCPU-hours y GB-hours de los recursos solicitados, por segundo y sin compromiso. Con Fargate Spot, las tareas interrumpibles (batch, workers de colas, CI/CD) consiguen hasta un 70% de descuento, y hoy también existen Fargate Savings Plans para compromiso sostenido.

La contrapartida es la flexibilidad que cedes: sin acceso al host no hay daemon sets en ECS, ni GPUs, ni optimizaciones a nivel de instancia, ni shared kernels entre tareas. La regla del examen: Fargate para cargas estándar (webs, APIs, workers) con el mínimo overhead; EC2 como launch type cuando aparecen GPU, daemons, requisitos de licencia por host o control del kernel. La arquitectura canónica que une todo lo aprendido — ALB repartiendo entre tareas Fargate en dos AZ — es un patrón que verás una y otra vez.

6Patrones serverless: eventos y orquestación

Una arquitectura event-driven desacopla productores y consumidores: algo ocurre (un evento) y un componente lo comunica sin que nadie sondee. El patrón mínimo usa Lambda como consumidor y una cola o bus como canal: con Amazon SQS los productores escriben mensajes y Lambda los sondea y procesa por lotes (modelo pull, ideal para absorber picos y reintentar fallos); con Amazon EventBridge los productores publican eventos en un bus enrutado por reglas hacia destinos diversos (modelo push, ideal para reaccionar a cambios de estado en tiempo casi real). El patrón se blindan con dead-letter queues para lo que fracasa tras reintentos y con idempotencia en el consumidor, porque "al menos una entrega" es la norma.

Cuando el flujo tiene varios pasos, decisiones o reintentos con lógica, el orquestador correcto es AWS Step Functions: defines una state machine en JSON/ASL con estados Task, Choice, Parallel, Map o Wait, y él gestiona el orden, los errores (retry/catch por excepción), la auditoría de cada ejecución y el versionado. Mover la lógica de orquestación fuera del código (el clásico "una Lambda llama a la siguiente") hacia Step Functions es una de las respuestas favoritas del examen cuando aparecen coordinate, orchestrate, retry logic o flujos de aprobación. Su primo moderno Amazon EventBridge Pipes conecta una fuente con un destino con filtrado y enriquecimiento ligeros.

El ecosistema serverless se completa con dos nombres que conviene reconocer. AWS AppSync ofrece APIs GraphQL gestionadas que resuelven datos desde DynamoDB, Lambda u otros backends, con suscripciones en tiempo real. El AWS Serverless Application Repository es el catálogo donde publicar y reutilizar aplicaciones serverless empaquetadas con SAM/CloudFormation. La regla de diseño detrás de todos: managed services glued by events — servicios gestionados pegados por eventos, sin servidores propios en ninguna capa.

Señales del examen

Tres reflejos finales de esta página: (1) containers without managing servers → Fargate; (2) least overhead para contenedores → Fargate; (3) ya usas Kubernetes → EKS. Y para flujos: SQS desacopla, EventBridge rutea eventos, Step Functions orquesta pasos. Casi toda pregunta serverless del SAA-C03 es una permutación de esos bloques.
