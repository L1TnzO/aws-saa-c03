Almacenamiento: objetos, bloques y archivosApéndice · D3 24%

El storage es uno de los territorios más rentables del SAA-C03: casi todas las preguntas de rendimiento y de costo acaban eligiendo entre S3, EBS, EFS y FSx. Esta página reúne las tres abstracciones, los servicios de cada una y los trucos de lectura para escoger la respuesta correcta a la primera.

Task Statement oficial 3.1
Determine high-performing and/or scalable storage solutions
Knowledge: hybrid storage solutions · storage services (S3, EFS, EBS) · storage types (object, file, block) — Skills: elegir el servicio y configuración que cumplen la demanda de rendimiento y escala

1Las tres abstracciones: objeto, bloque y archivo

AWS ofrece tres formas de organizar los bytes, y el examen espera que elijas la correcta sin dudar. El almacenamiento de objetos guarda datos como objetos planos con metadatos, se direcciona por HTTP y escala a cantidades ilimitadas: es el reino de Amazon S3. El almacenamiento en bloques presenta un disco virtual que la instancia formatea y gestiona a nivel de bloque, ideal para sistemas operativos y bases de datos: es Amazon EBS. El almacenamiento de archivos ofrece un sistema de archivos compartido con permisos POSIX o SMB, al que muchas instancias se montan a la vez: es el mundo de Amazon EFS y la familia Amazon FSx.

La distinción no es académica: cada abstracción impone un tipo de acceso, una latencia y un precio distintos. Si la pregunta menciona un disco de arranque o una base de datos en una única instancia, piensa en bloques; si habla de millones de archivos compartidos entre cientos de servidores Linux, piensa en archivos; si habla de contenido estático, backups, data lake o acceso por API, piensa en objetos.

Si aparece instance store junto a durable, es la opción trampa: es ephemeral, no persistente.

2Amazon S3 a fondo

Amazon S3 guarda datos en buckets (contenedores con nombre globalmente único) y objects (los datos + metadatos); un objeto puede medir de 0 bytes a 5 TB y por encima de 100 MB conviene multipart upload. Desde diciembre de 2020 S3 ofrece consistencia read-after-write fuerte para nuevos PUTs: una vez confirmada la escritura, cualquier lectura posterior ve el objeto — ya no existen los matices de consistencia eventual de las guías antiguas.

Storage classes: la tabla que cae en el examen

Todas las clases ofrecen la misma durabilidad de 11 nueves (99,999999999%); lo que cambia es la disponibilidad, el tiempo de recuperación y el precio. Memoriza la pareja duración mínima de facturación + tarifa de recuperación, porque ahí se decide el costo real.

S3 Intelligent-Tiering merece su propio párrafo porque es la respuesta cuando la pregunta dice unknown access patterns o minimize costs without performance impact. Mueve objetos entre tres niveles automáticos — Frequent Access, Infrequent Access (30 días sin acceso) y Archive Instant Access (90 días) — cobrando solo una pequeña cuota de monitoreo por objeto y sin tarifa de recuperación. Opcionalmente activas los niveles Archive Access (90 días) y Deep Archive Access (180 días) para datos que toleran recuperación asíncrona. Los objetos menores de 128 KB no se monitorean: siempre quedan en Frequent Access.

Lifecycle, versioning y MFA Delete

Las lifecycle configurations automatizan transiciones (Standard → IA → Glacier → Deep Archive) y expiraciones por prefijo o etiqueta, y es la respuesta estándar a most cost-effective over time. El versioning guarda cada variante de un objeto: borrar no destruye, solo inserta un delete marker, y puedes restaurar versiones anteriores. Es prerrequisito para MFA Delete y para la replicación. El MFA Delete exige un código MFA para eliminar versiones definitivamente — solo lo puede configurar el root account de la cuenta propietaria del bucket, un detalle que el examen pregunta directamente.

Cifrado: cuatro variantes SSE + TLS

Para el examen necesitas las cuatro formas de server-side encryption y cuándo exige cada una. En tránsito, S3 habla HTTPS/TLS en su endpoint REST, y una bucket policy con condición aws:SecureTransport = false deniega cualquier petición sin cifrar.

Replicación: CRR, SRR y RTC

La replicación de S3 copia objetos de forma automática y asíncrona entre buckets (misma cuenta o cuentas distintas). Cross-Region Replication (CRR) replica entre Regiones: cumplimiento geográfico, menor latencia para usuarios lejanos y DR. Same-Region Replication (SRR) replica dentro de la misma Región: agregar logs en un solo bucket, sincronizar cuentas de producción y test, o soberanía de datos. S3 Replication Time Control (RTC) añade un SLA que replica el 99,99% de los objetos en 15 minutos. La replicación en vivo no copia objetos previos: para esos existe S3 Batch Replication; y para failover entre Regiones se combina replicación bidireccional con Multi-Region Access Points.

Presigned URLs, web hosting, eventos y más

Varias features de S3 son respuestas rápidas en el examen. Las presigned URLs comparten un objeto o permiten subirlo a tu bucket con credenciales temporales, sin hacerlo público ni crear usuarios IAM: piensa en ellas ante allow a partner to download one file temporarily. El static website hosting sirve index/error documents en un endpoint web del bucket; ese endpoint no da HTTPS por sí solo, así que la respuesta con HTTPS es poner Amazon CloudFront delante. Las event notifications disparan SNS, SQS, Lambda o EventBridge cuando llega un objeto: el patrón decoupled típico de subida de archivos. Requester Pays traslada al lector el costo de transferencia, ideal para compartir datasets grandes con terceros. S3 Batch Operations ejecuta copias, restauraciones o invocaciones Lambda sobre billones de objetos con un manifiesto. Por último, los Multi-Region Access Points exponen un endpoint global que enruta a buckets de varias Regiones con failover controlado.

Señales del examen

share an object with a vendor for 5 minutes → presigned URL (nunca credenciales IAM). trigger a process when a file is uploaded → S3 event notifications (o EventBridge si necesitas enrutamiento avanzado). HTTPS for a static website → CloudFront delante del bucket, no el website endpoint solo. durability 11 nines → cualquier clase de S3: no confundas durabilidad con disponibilidad.

3Amazon EBS: bloques para tu instancia

Amazon EBS provee volúmenes de bloque persistentes y adjuntos a una instancia EC2 en una sola Availability Zone. Un volumen EBS sobrevive al stop de la instancia y puede re-adjuntarse a otra instancia de la misma AZ; montarlo en otra AZ exige moverlo vía snapshot. Para exprimir las IOPS provisionadas conviene usar instancias EBS-optimized. La distinción clave al dimensionar: las IOPS mandan en I/O pequeño y aleatorio (SSD), mientras que el throughput (MiB/s) manda en lecturas grandes y secuenciales (HDD).

Snapshots: incrementales, archive tier y FSR

Un snapshot es una copia point-in-time incremental: solo se guardan los bloques que cambiaron desde el snapshot anterior, lo que abarata el almacenamiento (que vive en S3, aunque no accesible directamente). El primer snapshot es siempre completo. Puedes compartirlos entre cuentas, copiarlos a otras Regiones y construir AMIs. El snapshot archive tier los mueve a un nivel un 75% más barato a cambio de una recuperación de 24-72 horas. El Fast Snapshot Restore (FSR) elimina la latencia de inicialización del primer acceso tras restaurar un volumen — útil para bases de datos grandes — pero se paga por AZ y por snapshot, así que el examen lo castiga si lo eliges sin necesidad.

Multi-Attach, RAID 0 e instance store

El EBS Multi-Attach permite adjuntar un volumen io1/io2 a hasta 16 instancias de la misma AZ: lo usan aplicaciones cluster-aware que gestionan la coherencia de escritura ellas mismas (Oracle RAC, por ejemplo). Si necesitas más de 256.000 IOPS o 4 GiB/s, la respuesta clásica es RAID 0: repartir datos entre varios volúmenes EBS para sumar rendimiento (a costa de tolerancia a fallos). Y no confundas EBS con el instance store: los discos efímeros viven físicamente en el host, ofrecen latencia brutal, pero se pierden al stop/terminate de la instancia — perfectos para caches, buffers y datos temporales, y trampa mortal ante cualquier requisito de durable.

Error común

Elegir st1/sc1 para una base de datos porque "es más barato por GB": las bases de datos hacen I/O aleatorio pequeño y necesitan SSD (gp3/io2); st1 es para streaming secuencial. Otro: activar FSR "porque sí" cuando la pregunta no pide eliminar la latencia de primera lectura — cuesta por AZ y es cost overhead.

4Amazon EFS: archivos compartidos NFS

Amazon EFS es un sistema de archivos NFSv4 totalmente administrado y elástico: crece hasta petabytes sin aprovisionar nada y se paga por lo usado. Un filesystem Regional replica los datos en múltiples AZ de la Región (el recomendado); la variante One Zone vive en una sola AZ y cuesta menos. El acceso ocurre por mount targets: una ENI que creas en cada AZ de tu VPC para que las instancias monten el sistema sin cruzar tráfico entre AZs innecesariamente. Lo montan a la vez miles de instancias EC2, contenedores ECS/EKS e incluso Lambda, lo que lo convierte en la respuesta por defecto a shared storage for many Linux instances.

Modos de throughput y clases de almacenamiento

EFS separa el modo de rendimiento (General Purpose vs Max I/O, herencia del examen) del modo de throughput. El modo Elastic (por defecto, recomendado) escala el throughput automáticamente con la actividad; el modo Bursting da un throughput base ligado al tamaño de los datos con créditos de burst; y el modo Provisioned permite fijar MB/s por encima de lo que el tamaño justificaría, para datasets pequeños que exigen mucho rendimiento. En costo, EFS tiene clases Standard, Infrequent Access (IA) y One Zone-IA; la lifecycle management mueve archivos sin acceso (p. ej. tras 30 días) a IA y los devuelve transparentemente cuando alguien los lee — el paralelo exacto de Intelligent-Tiering pero a nivel de archivo.

5La familia FSx: Lustre, Windows, ONTAP y OpenZFS

Cuando el sistema de archivos genérico no basta, Amazon FSx ofrece cuatro sabores especializados, todos totalmente administrados. La lógica de elección es el ecosistema: FSx no compite con EFS en elasticidad; gana por compatibilidad y rendimiento bruto con la tecnología que tu carga ya usa. Para el examen, identifica la palabra clave de cada variante y la respuesta sale sola.

6Archivo profundo, híbrido y backups centralizados

S3 Glacier en profundidad

El examen llama "Glacier" a las tres clases de archivo dentro de S3 (Instant Retrieval, Flexible Retrieval y Deep Archive), pero existió un servicio independiente de bóvedas: el Amazon Glacier original organizaba archivos en vaults con su propia API REST y ya no acepta clientes nuevos. De él heredas dos conceptos que aún aparecen: el vault lock (política WORM inmutable para cumplimiento) y los modos de recuperación de Flexible Retrieval. En las clases de S3, recuperar un objeto de Flexible/Deep Archive exige llamar antes a RestoreObject: expedited (1-5 minutos, más caro, para emergencias), standard (3-5 horas) y bulk (5-12 horas, gratis) — y en Deep Archive, standard 12 horas y bulk 48 horas. Deep Archive es la respuesta automática a cheapest long-term archive o compliance 7 years.

AWS Storage Gateway: el puente híbrido

AWS Storage Gateway conecta aplicaciones on-premises con almacenamiento en la nube exponiendo protocolos estándar (NFS, SMB, iSCSI o cintas virtuales) con una cache local que sirve los datos calientes con baja latencia mientras el dato primario vive en AWS. Es la respuesta a on-premises application needs low-latency access to cloud storage o extend data center without new hardware. Se despliega como appliance virtual (VMware/Hyper-V/EC2) o hardware appliance dedicado.

AWS Backup: un solo plano de backups

AWS Backup centraliza y automatiza la protección de datos a través de servicios — EBS, EFS, RDS, DynamoDB, FSx, Storage Gateway — con backup plans basados en horario, retención, lifecycle a cold storage y asignación por etiquetas. Los backups viven en backup vaults cifrados con KMS, se pueden copiar cross-Region y cross-account dentro de Organizations, lo que cubre DR y cumplimiento con un solo servicio. Sus backups son incrementales tras la primera copia y Audit Manager genera la evidencia de cumplimiento. Ante centralize and automate backups across services, es la respuesta; ante un solo servicio, usa la feature nativa (snapshots EBS, backups automáticos RDS).

Señales del examen

on-prem app requiring low-latency reads, data must live in S3 → S3 File Gateway. replace tape library / backup software keeps working → Tape Gateway. central backup policy across AWS services, cross-region copies → AWS Backup. Y el clásico: cheapest way to retain 7 years of audit archives → S3 Glacier Deep Archive, no Flexible.

Los cuatro reflejos innegociables

1) Durabilidad de 11 nueves = todas las clases de S3; no la confundas con disponibilidad. 2) "Cheapest long-term archive" → Deep Archive, siempre. 3) OS y bases de datos viven en bloque (EBS). 4) Compartir entre muchas instancias Linux con adjunción masiva → EFS; Multi-Attach de EBS solo existe en io1/io2 y en la misma AZ. Domina estos cuatro y ya tienes la mitad de las preguntas de storage del SAA-C03.

Tip de estudio

Escribe de memoria la tabla de storage classes tres veces en días distintos: clase → tiempo de acceso → mínimos de días → caso. Es la tabla con mayor densidad de preguntas por centímetro cuadrado de todo el examen, y las distracciones (Standard-IA vs One Zone-IA vs Glacier IR) se distinguen solo por dos palabras del enunciado.
