Tablas comparativas para decidir en el examen Service decision tables

El SAA-C03 no pregunta definiciones: presenta un escenario y espera que elijas el servicio correcto entre cuatro opciones plausibles — estas tablas condensan las diez comparaciones que más se repiten.

Extras Material de decisión rápida Repaso global · Fases 1-8

Leer cualquier task statement del exam guide es encontrar siempre la misma estructura: design a solution que sea secure, resilient, high-performing y cost-optimized. El examen es, en la práctica, un torneo de comparaciones: S3 frente a EBS, Aurora frente a RDS, Transit Gateway frente a peering, Spot frente a Reserved. Las cuatro opciones suelen ser arquitecturas válidas y solo una es la óptima para el criterio señalado con frases como least operational overhead o most cost-effective: lo que puntúa es la matriz mental de "dado este requisito, gana este servicio".

Esta página es esa matriz, condensada en diez tablas con los mismos criterios de fila — qué es, cuándo elegir, caso del examen y señal del enunciado. Lee la fila "señal" la víspera del examen y la fila "cuándo elegir" durante el repaso por dominios. Los datos están verificados contra la documentación oficial y las páginas de tema de este curso.

Para el examen
Antes de mirar las opciones, subraya el criterio de optimización ("most cost-effective", "least operational overhead") y el requisito duro (RPO/RTO, latencia, protocolo). Con esas dos líneas, dos opciones caen por el requisito, una más por el criterio, y queda la correcta.

1 · Almacenamiento: S3, EBS, EFS y FSx

La primera pregunta de storage es siempre el tipo de acceso: objetos por API, bloques adjuntos a una instancia o archivos montados por muchas a la vez. S3 es object storage de once nueves de durabilidad; EBS es el disco de una EC2; EFS es el NFS elástico compartido entre AZs; y FSx cubre los casos "purpose-built": Windows con SMB y Active Directory, HPC con Lustre. El diagrama resume la ramificación y la tabla añade las señales.

Cuándo elegirAssets, backups, data lakes, sitio estático, cualquier dato vía APIBoot disk y datos de una instancia que necesita latencia de milisegundos e IOPSDirectorios home, shares Linux, contenido compartido entre AZsLift-and-shift de apps Windows, shares con ACLs de AD, HPC/ML con datasets masivos

2 · Bases de datos: RDS, Aurora, DynamoDB y ElastiCache

Aquí la pregunta de fondo es el modelo de datos y la escala. RDS es el relacional gestionado para SQL estándar; Aurora es el relacional de alto rendimiento compatible con MySQL/PostgreSQL, con hasta 15 read replicas; DynamoDB es el key-value serverless de single-digit millisecond latencia a cualquier escala; y ElastiCache es la capa in-memory que descarga lecturas y guarda sesiones. La trampa típica: responder DynamoDB cuando el esquema es relacional, o RDS cuando el enunciado pide "any scale, key-value".

CriterioRDSAuroraDynamoDBElastiCache
Qué esRelacional gestionado (MySQL, PostgreSQL, etc.) con Multi-AZ opcional y read replicasMySQL/PostgreSQL compatible; storage replicado en 3 AZs, hasta 15 réplicas, Serverless y Global DatabaseKey-value serverless; RCU/WCU provisioned u on-demand; global tablesIn-memory Redis/Memcached: cache y session store de microsegundos
Cuándo elegirSQL estándar, esquema fijo, migrar app existente con mínima administraciónMáximo rendimiento relacional, escalado agresivo de lecturas, DR globalAcceso por clave a escala masiva y tráfico impredecible, sin gestionar servidoresQuitar carga de lectura a la base de datos; sesiones compartidas entre instancias
Caso del examen"existing MySQL application, minimal administration""MySQL-compatible, scale reads to 15 replicas, <1 s cross-region""single-digit milliseconds at any scale, unpredictable traffic""reduce database load, microsecond reads, shared session state"
Señal del enunciadorelational · managedcompatible + performancekey-value · serverlessin-memory · cache

3 · Mensajería y streaming: SQS, SNS, EventBridge y Kinesis

La unidad que viaja decide la elección: trabajo (mensajes que un consumidor procesa y borra), notificación (el mismo mensaje a muchos suscriptores), evento (hechos que se filtran por patrón) o flujo continuo (registros ordenados por clave que varias apps leen y releen). SQS es la cola con buffer y reintentos; SNS el topic pub/sub; EventBridge el bus que enruta por contenido; Kinesis el stream con shards y retención. No compiten tanto como se cree: lo idiomático es combinarlos (EventBridge que filtra y dispara a SQS, SNS que hace fan-out).

CriterioSQSSNSEventBridgeKinesis
Qué esCola pull con buffer durable, at-least-once, visibility timeout y DLQTopic pub/sub push a suscriptores: SQS, Lambda, email, SMSBus serverless con rules que filtran eventos por patrón; fuentes AWS y SaaSStreaming por shards; orden por partition key, retención y relectura, varios consumidores
Cuándo elegirDesacoplar productor y consumidor, absorber picos, reintentosNotificar a N destinos heterogéneos; fan-out hacia colasEnrutar por contenido; reaccionar a servicios AWS/SaaS; SchedulerClickstream, logs, analytics en tiempo real; cargar a S3 con Firehose
Caso del examen"decouple components, buffer orders, retry failures""notify multiple systems at once", "fan-out""route events based on content", "react to S3 uploads""real-time analytics, replay the stream, multiple consumers"
Señal del enunciadoqueue · poll · decoupletopic · push · pub/subevent pattern · filteringstream · shard · real-time

4 · Load balancers: ALB, NLB y GWLB

El protocolo y el "qué balancea" separan a los tres. El ALB entiende HTTP (capa 7) y decide por path, host o header — el LB de microservicios y contenedores. El NLB opera en capa 4 con millones de peticiones por segundo, flow hash determinista, preserva la IP del cliente y ofrece IP estática por AZ. El GWLB funciona en capa 3 e inserta appliances (firewalls, IDS/IPS) en el camino del tráfico con GENEVE 6081. Si el enunciado menciona URL o headers: ALB; UDP o IPs fijas: NLB; inspección inline: GWLB.

CriterioALBNLBGWLB
Qué esCapa 7: listeners con reglas por path, host y header; target groups con health checksCapa 4: millones de req/s, flow hash por conexión, IP estática por AZ (EIP por subnet)Capa 3: gateway transparente + balanceo de appliances con GENEVE 6081
Cuándo elegirMicroservicios, ECS/EKS, rutas por URL, WAF, redirecciones HTTPRendimiento extremo, TCP/UDP/QUIC, gaming, IoT, preservar IP del clientePoner firewalls o IDS/IPS inline; appliances de terceros
Caso del examen"route /api to a different target group""static IP for the load balancer", "UDP traffic""inspect all traffic with a third-party firewall"
Señal del enunciadoLayer 7 · URL · headersLayer 4 · static IPLayer 3 · inline appliance

5 · Compra de EC2: On-Demand, Reserved, Savings Plans y Spot

Dominio 4 puro: la misma instancia se factura de cuatro maneras y el examen pregunta por tolerancia a interrupción y predecibilidad del uso. On-Demand paga por segundo sin compromiso. Las Reserved Instances comprometen 1 o 3 años sobre atributos de instancia (Standard descuenta más; Convertible permite cambiar familia; la zonal reserva capacidad). Los Savings Plans comprometen un gasto por hora: el Compute SP es el más flexible — cubre EC2 sin importar familia, tamaño, OS o región, y también Fargate y Lambda, hasta 72%. Spot compra capacidad sobrante con descuentos profundos a cambio de una interrupción avisada con 2 minutos; su gasto no cuenta para los compromisos de Savings Plans.

CriterioOn-DemandReserved InstancesSavings PlansSpot
Qué esPago por segundo, cero compromiso, precio de listaCompromiso 1/3 años sobre atributos de instancia; Standard, Convertible y zonalCompromiso de gasto USD/h; Compute SP (EC2 + Fargate + Lambda) o EC2 Instance SP (una familia)Capacidad sobrante de AWS; interrupción con aviso de 2 minutos
Cuándo elegirCargas cortas, irregulares o que no pueden interrumpirseEstado esteady 24/7 de un tipo de instancia concreto; reservar capacidad en una AZFlexibilidad de familia/región o uso mixto EC2 + Fargate + LambdaBatch, CI/CD, big data; cualquier workload tolerante a interrupción
Caso del examen"short-term, spiky, cannot be interrupted""steady state for 3 years, specific instance family""flexible across instance families, include Fargate""cheapest compute for a fault-tolerant batch job"
Señal del enunciadono commitmentreserved capacity in an AZup to 72% · flexible2-minute interruption notice

6 · Disaster recovery: las cuatro estrategias

El whitepaper oficial ordena la DR en una escalera de costo: backup and restore, pilot light, warm standby y multi-site active/active. La pregunta da un RTO y un RPO y pide la estrategia más barata que los cumpla: subraya ambos números, clasifícalos en horas, minutos o segundos, y baja por la escalera hasta la primera fila que cumpla sin holgura. Las tres primeras son activo/pasivo; AWS Resilience Hub es la respuesta cuando piden "validar" el cumplimiento.

EstrategiaQué existe antes del desastreRPO / RTO típicosCostoSeñal del enunciado
Backup and restoreSolo copias de datos replicadas a otra región; infraestructura por provisionarHoras / horasEl más bajo"tolerates hours of downtime and data loss"
Pilot lightCapa de datos crítica replicada y encendida; cómputo se lanza al fallarMinutos / decenas de minutosBajo"core data always on, rest on failover"
Warm standbyEntorno completo a escala reducida corriendo en la segunda regiónSegundos / pocos minutosMedio"scaled-down copy, scale up on failover"

7 · ElastiCache: Redis o Memcached

Dentro de ElastiCache, el motor es la decisión. Redis aporta replicación con failover Multi-AZ, persistencia, backups, cluster mode y estructuras ricas (sorted sets, pub/sub) — el session store por excelencia. Memcached es deliberadamente simple: multi-hilo, sin replicación, sin persistencia y sin failover; si un nodo muere, sus datos desaparecen. La regla práctica: cualquier mención de alta disponibilidad, sesiones o estructuras de datos apunta a Redis; Memcached solo sobrevive en escenarios de cache efímero y simple.

CriterioRedisMemcached
Qué esData store in-memory con replicación, failover Multi-AZ, persistencia y cluster modeCache clave-valor multi-hilo, sin replicación ni persistencia
Cuándo elegirHA, sesiones compartidas, leaderboards, pub/sub, backup/restoreCache de objetos simple y efímero; paralelismo de nodos grandes
Caso del examen"session store that survives instance replacement""simple, ephemeral object cache"
Señal del enunciadoMulti-AZ · failover · sorted setssimple · no persistence

8 · Storage classes de S3

Todas las clases comparten los once nueves de durabilidad: lo que cambia es disponibilidad, precio, velocidad de recuperación y duración mínima facturable. Las clases IA cobran retrieval y 30 o 90 días mínimos aunque expires antes; las Glacier exigen restore salvo Instant Retrieval, que se lee en milisegundos. Con patrones desconocidos o cambiantes, Intelligent-Tiering mueve objetos entre tiers automáticamente sin retrieval fees — la respuesta a "minimize cost, no operational overhead". Y el señuelo: RRS está desaconsejado por la propia documentación.

9 · Conectividad de VPC: peering, Transit Gateway y PrivateLink

Tres formas de conectar redes, tres unidades: el peering conecta dos VPCs punto a punto (no transitivo, CIDRs sin solape); el Transit Gateway es el hub que interconecta N VPCs, VPN y Direct Connect con route tables segmentables — la respuesta a cualquier malla grande; y PrivateLink expone o consume un servicio concreto por IP privada, sin peering ni rangos coordinados. La pregunta decodificadora: ¿acceso a una red (peering/TGW) o a un servicio (PrivateLink)? Si el enunciado insinúa "route through a third VPC", la respuesta es TGW: el peering nunca transita.

CriterioVPC peeringTransit GatewayPrivateLink
Qué esConexión 1:1 entre dos VPCs, no transitiva, CIDRs sin solapeHub de tránsito para N VPCs, VPN, DX y otros TGWs; route tables por attachmentAcceso privado a un servicio puntual vía interface endpoint (ENI) o gateway endpoint (ruta)
Cuándo elegirDos VPCs estables con ancho de banda directoMallas grandes, enrutado transitivo, topología híbrida, segmentaciónConsumir S3/DynamoDB/SaaS sin IGW ni NAT; ofrecer tu servicio a otras cuentas
Caso del examen"connect two VPCs with minimal cost""connect many VPCs, all-to-all, minimal management""access S3 privately from a private subnet"
Señal del enunciadoone-to-one · non-transitivehub-and-spoke · transitiveservice not network · private IP

10 · CloudFront o Global Accelerator

Ambos "mejoran la latencia global", pero optimizan cosas distintas: CloudFront mueve el contenido hacia las edge locations (caché con TTL e invalidación, menos carga en el origin); Global Accelerator mueve el tráfico del usuario por la red global de AWS hasta el endpoint regional más cercano, con dos IPs anycast estáticas y health checking. Si la carga es HTTP/S cacheable, CloudFront; si es TCP/UDP puro o exige IPs fijas, Global Accelerator. El distractor favorito: responder GA a un escenario puramente web cacheable — GA no cachea nada.

CriterioCloudFrontGlobal Accelerator
Qué esCDN: caché de contenido HTTP/S en edge locations, TTL e invalidación2 IPs anycast estáticas que llevan el tráfico por la red global AWS hasta endpoints regionales
Cuándo elegirWeb, APIs cacheables, descargas, streaming; reducir carga del originGaming, IoT, VoIP (TCP/UDP), IPs fijas para allowlists, failover entre regiones
Caso del examen"serve static assets worldwide with low latency""clients allowlist two static IPs", "global UDP application"
Señal del enunciadocache · TTL · distributionanycast · static IP · health checking
Checkpoint — lo que debes recordar
  1. Identifica el criterio de optimización antes de leer las opciones.
  2. Tipo de acceso decide el storage: objeto / bloque / archivo; modelo de datos decide la base: relacional / clave-valor / cache.
  3. La unidad que viaja decide la mensajería: trabajo, aviso, evento o flujo.
  4. Protocolo decide el LB: L7 (ALB), L4 (NLB), L3 inline (GWLB).
  5. Interrumpible → Spot; esteady → RI/SP; flexible + Fargate/Lambda → Compute SP.
  6. DR: la estrategia más barata que cumpla RTO y RPO.
  7. Malla o tránsito → TGW; acceso a un servicio → PrivateLink.
  8. Web cacheable → CloudFront; TCP/UDP con IPs fijas → Global Accelerator.
