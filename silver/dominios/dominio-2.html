D2: Design Resilient Architectures 26% of exam

El Dominio 2 mide si tus arquitecturas aguantan: que absorban picos de tráfico sin rediseño y que sobrevivan a fallos de instancias, AZs o regiones completas. Solo tiene dos task statements, pero cada uno es un continente: scalable and loosely coupled architectures (colas, eventos, orquestación, microservicios, serverless, contenedores, caching, multi-tier) y highly available and/or fault-tolerant architectures (multi-AZ, multi-region, estrategias de disaster recovery, RPO/RTO, failover, infraestructura inmutable y backups). Con un 26% de peso equivale a unas 13 de las 50 preguntas evaluadas, y son las preguntas más "de arquitecto" del examen completo: te dan un requisito de negocio y hay que escoger la pieza que lo cumple.

Cómo estudiarlo: primero los patrones y después las estrategias. El patrón estrella es el decoupling: cualquier escenario donde dos componentes escalan a ritmos distintos o donde uno puede caer sin arrastrar al otro apunta a SQS, SNS o EventBridge. Después, estudia el failover como una escalera de coste creciente: multi-AZ primero (región), luego multi-region con las cuatro estrategias de DR del Task 2. La tabla RTO/RPO de esta página es de las más rentables de memorizar del examen entero, porque casi todas las preguntas de DR se resuelven eligiendo el punto de esa escalera que cumple los dos números que da el enunciado.

Task Statement 1: Design scalable and loosely coupled architectures

Este task statement evalúa si sabes romper dependencias para que cada componente escale y falle por separado. El repertorio: SQS como buffer entre productores y consumidores (con visibility timeout y DLQ), SNS para fan-out a muchos suscriptores, EventBridge para event-driven con reglas y Step Functions para orquestar workflows con Retry/Catch y ramas paralelas. Encima, API Gateway como puerta HTTPS con throttling, Lambda y Fargate como serverless para cargas impredecibles, ECS/EKS para empaquetar microservicios o legacy, y capas stateless detrás de un ALB para escalar horizontalmente. El caching (ElastiCache, CloudFront) también pertenece a este task statement como palanca de escala, igual que las read replicas para leer y los tres tipos de storage (object, file, block) al escoger persistencia. La señal maestra: si el enunciado pide que los componentes "fail independently" o "scale at different rates", la respuesta contiene una cola o un bus de eventos.

Si el enunciado dice…La respuesta apunta a…
"the web tier must not wait for orders that take hours to process"SQS entre frontend y workers (buffer, reintentos, DLQ)
"every subsystem must receive a copy of each order event"SNS fan-out a colas SQS (o EventBridge con múltiples targets)
"a workflow needs retries, parallel branches and error handling"Step Functions (Retry con backoff, Catch, Choice, Map)
"unpredictable spiky image processing, no servers to manage"Event-driven con Lambda (o Fargate si ya hay contenedores)
"the database is overwhelmed by read traffic"Read replicas + ElastiCache (y CloudFront para contenido estático)

Task Statement 2: Design highly available and/or fault-tolerant architectures

La alta disponibilidad empieza por eliminar single points of failure, y la unidad mínima es la AZ: un ASG con instancias en varias AZs detrás de un ALB con health checks, y RDS Multi-AZ con standby síncrona y failover automático. Cuando el riesgo es la región entera entran las cuatro estrategias de DR, ordenadas por coste y por velocidad de recuperación: backup and restore (solo backups cross-region, RTO de horas), pilot light (el core mínimo encendido en la segunda región), warm standby (una copia reducida pero completa y corriendo) y active-active (dos regiones sirviendo tráfico, con Route 53 y Aurora Global Database o global tables). El criterio de elección siempre son los dos números del negocio: RPO (cuánto dato puedes perder) y RTO (cuánto puedes tardar en volver). El task statement añade durabilidad de datos (S3 y AWS Backup cross-region), infraestructura inmutable con CloudFormation, visibilidad con X-Ray, cuotas de servicio en el entorno de standby y el caso "legacy que no se puede modificar", donde RDS Proxy y colas absorben tormentas de conexiones sin tocar el código.

Si el enunciado dice…La respuesta apunta a…
"must tolerate the failure of one AZ with no manual intervention"Multi-AZ: ALB + ASG en varias AZs + RDS Multi-AZ
"cheapest possible DR, RTO of hours"Backup and restore con backups cross-region
"RTO of minutes, moderate cost, core always ready"Pilot light (core encendido) o warm standby (copia reducida activa)
"users must not notice a regional failure; both regions serve traffic"Active-active: Route 53, Aurora Global Database / DynamoDB global tables
"connection surges crash a legacy database; the app cannot be modified"RDS Proxy (pooling) — o SQS para absorber picos de escritura
Trampa clásica
Confundir RDS Multi-AZ con una read replica: Multi-AZ es HA dentro de la región (standby pasiva, réplica síncrona, failover automático, no sirve lecturas), mientras que la read replica es escalado de lectura (asíncrona, legible, promocionable). Otra confusión rentable para los distractors: "Multi-AZ" NO es disaster recovery regional — si el enunciado pierde la región, necesitas cross-region (réplica cross-region, Aurora Global Database, backups en otra región).

Ruta de estudio de este dominio

Ordena el repaso como se construye una arquitectura resiliente: primero repartir tráfico y escalar, después desacoplar, a continuación las bases de datos disponibles, y al final el DR y la observabilidad que lo verifica todo:

  1. Load balancers: ALB/NLB/GWLB — health checks y distribución multi-AZ del Task 2.
  2. Auto Scaling — escala horizontal y políticas que siguen la demanda.
  3. SQS y SNS — el decoupling y el fan-out: el corazón del Task 1.
  4. EventBridge — event-driven y Scheduler.
  5. Step Functions — orquestación con retry y ramas.
  6. Lambda — serverless para cargas variables.
  7. ECS, EKS y Fargate — microservicios empaquetados.
  8. RDS: Multi-AZ y réplicas — la distinción HA vs escalado de lectura.
  9. Aurora — endpoints y Global Database para multi-region.
  10. DynamoDB — global tables y diseño por particiones.
  11. S3 y Glacier — durabilidad de 11 nueves y replicación CRR.
  12. Route 53 (DNS) — failover routing, el interruptor global.
  13. CloudFront y Global Accelerator — orígenes multi-región y edge.
  14. Disaster Recovery (RTO/RPO) — las cuatro estrategias en detalle.
  15. AWS Backup — planes, cross-region y cross-account.
  16. CloudWatch y X-Ray — alarmas y visibilidad del workload.

Repaso rápido: 5 preguntas de señal

Cinco escenarios cortos en inglés con su respuesta y una línea de razonamiento. Cada uno corresponde a un patrón de los de arriba; si dudas, la página de tema de la ruta lo desarrolla:

D2-R1 Order intake receives bursts of thousands of requests, but fulfillment takes hours. The web tier must not block. What decouples the tiers?
Amazon SQS queue
La cola absorbe los picos, los workers procesan a su ritmo y un DLQ recoge los fallos: decoupling clásico.
D2-R2 A company requires automatic database failover to a standby copy in a second Availability Zone. Which RDS feature provides this?
RDS Multi-AZ deployment
Réplica síncrona a un standby pasivo en otra AZ y failover automático; las read replicas son para lecturas, no HA.
D2-R3 A non-critical internal application needs the lowest-cost DR strategy and tolerates an RTO of several hours. Which strategy fits?
Backup and restore
Solo pagas backups cross-region y reconstruyes bajo demanda: el escalón más barato de la escalera de DR.
D2-R4 Each subsystem must receive its own copy of every order event for independent processing. Which pattern fits?
SNS fan-out to SQS queues
Un topic SNS entrega una copia a cada cola SQS suscrita; cada sistema consume a su ritmo y con su DLQ.
D2-R5 A global application needs a database layer with an RPO under 1 second across AWS Regions. Which solution meets this?
Aurora Global Database
Replica de la región primaria a hasta 10 regiones secundarias con latencia de replicación típica por debajo de 1 segundo.
Checkpoint — lo que debes recordar de D2
  1. Decoupling es el patrón estrella: SQS entre componentes que escalan o fallan a distinto ritmo.
  2. SQS es at-least-once: visibility timeout, DLQ para fallos, FIFO si importa el orden o el exactly-once.
  3. SNS = push y fan-out a N suscriptores; EventBridge = eventos estructurados con reglas; Step Functions = orquestación con Retry/Catch.
  4. Capas stateless escalan horizontalmente con ASG multi-AZ detrás de un ALB.
  5. Multi-AZ ≠ read replica: HA síncrona con failover automático vs escalado de lectura asíncrono.
  6. Multi-AZ ≠ DR regional: perder la región exige cross-region (réplicas, Aurora Global, backups).
  7. Escalera de DR de menor a mayor coste: backup & restore → pilot light → warm standby → active-active.
  8. RPO = dato que puedes perder; RTO = tiempo hasta volver: elige el escalón que cumpla ambos.
  9. S3 y DynamoDB ya replican multi-AZ de fábrica: no rediseñes lo que el servicio garantiza.
  10. Route 53 (failover routing) y RDS Proxy (tormentas de conexiones de legacy) son las dos ayudas que el examen premia en failover.
