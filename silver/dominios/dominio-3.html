El Dominio 3 es el más ancho del examen: cinco task statements, uno por familia de servicios — almacenamiento, cómputo elástico, bases de datos, redes e ingesta/transformación de datos — y con un 24% de peso equivale a unas 12 de las 50 preguntas evaluadas. El enfoque no es "más grande es mejor", sino the right tool for the access pattern: elegir el servicio cuya forma natural de rendimiento coincide con la métrica que pide el enunciado (IOPS, throughput, latencia sub-milisegundo, millones de eventos por segundo). Casi todas las preguntas de D3 incluyen una cifra o una unidad: "sub-millisecond", "millions of requests", "sequential throughput"; tu trabajo es traducir esa cifra al servicio que la entrega de fábrica.

Cómo estudiarlo: por familia, no por servicio. Memoriza los dos mapas de esta página (dos porque el dominio es grande) y las cinco señales de la tabla de cada task statement. Las preguntas de D3 se contestan por reconocimiento: "shared file system" → EFS, "aggregate throughput for HPC" → FSx for Lustre, "cache" → ElastiCache o DAX. Y repasa el vocabulario de métricas en inglés: aquí el enunciado se juega en una palabra ("provisioned", "burstable", "on-demand").

Task Statement 1: Determine high-performing and/or scalable storage solutions

Evalúa escoger entre object, file and block storage según el patrón de acceso. S3 para objetos vía API, con rendimiento por prefijo y multipart upload para paralelizar; EBS para volúmenes de bloque con gp3 de línea base alta e io2/io2 Block Express cuando el enunciado pide IOPS garantizadas y latencia uniforme; EFS para un sistema de archivos NFS compartido que crece y sirve a cientos de instancias Linux; y FSx for Lustre cuando el HPC pide throughput agregado masivo. Añade el matiz híbrido: Storage Gateway da caché local de S3 a aplicaciones on-premises y DataSync mueve datos hacia y desde AWS. Las decisiones clave: ¿acceso por objeto, bloque o archivo compartido?; ¿IOPS provisionadas o throughput secuencial barato?; ¿un consumidor o cientos en paralelo?

Si el enunciado dice…La respuesta apunta a…
"a shared file system for hundreds of Linux instances"EFS (NFS, mount targets multi-AZ)
"an HPC workload needs massive aggregate throughput"FSx for Lustre (sistema de archivos paralelo)
"boot volume with guaranteed 50,000 IOPS and sub-ms latency"EBS io2 / io2 Block Express
"billions of small files accessed by key over HTTP"S3 (rendimiento por prefijo + multipart)
"on-premises application needs low-latency access to S3 data"Storage Gateway con caché local

Task Statement 2: Design high-performing elastic compute solutions

Evalúa dimensionar y desacoplar el cómputo. La primera palanca es la familia de instancia: c para CPU-bound, r para memoria, i para I/O de storage local, p (GPU) para ML, m equilibrada — el right-sizing que también reaparece en D4. La segunda es la elasticidad: EC2 Auto Scaling con políticas que siguen métricas, AWS Auto Scaling para planes multi-servicio, y desacoplar con colas para que cada componente escale por separado. La tercera es el modelo de ejecución: Lambda para eventos con carga impredecible (donde ajustar la memoria escala CPU y capacidad a la vez), Fargate para tasks aisladas con su propia ENI, Batch para miles de jobs con dependencias y EMR para clusters de big data con Spark o Hadoop. Mide también las condiciones de escala: qué métrica dispara el scale-out y con qué métricas de CloudWatch la defines.

Si el enunciado dice…La respuesta apunta a…
"video transcoding is CPU-bound and must finish nightly"Familia c + ASG programado (Spot si es interrumpible)
"run Spark/Hadoop clusters without managing the framework"Amazon EMR
"thousands of independent batch jobs with priorities"AWS Batch (colas y prioridades)
"event-driven thumbnails with unpredictable volume"Lambda (concurrency) o Fargate con ECS
"per-task isolation with its own ENI and no EC2 to manage"Fargate (tasks con ENI propia)

Task Statement 3: Determine high-performing database solutions

Evalúa casar el patrón de datos con el motor. Read-intensive → read replicas (o el reader endpoint de Aurora) y ElastiCache por delante; key-value a escala con latencia de un dígito → DynamoDB, con DAX si hace falta microsegundos de caché; relacional compatible MySQL/PostgreSQL con más throughput → Aurora, con hasta 6x el rendimiento de MySQL estándar y storage que auto-escala; tormentas de conexiones (típicas de Lambda) → RDS Proxy con pooling; latencia uniforme → Provisioned IOPS. El task statement también distingue motores por caso: analítico columnar (Redshift), in-memory (ElastiCache), serverless (Aurora Serverless, DynamoDB on-demand) y las migraciones homogéneas frente a heterogéneas. La decisión maestra: primero el patrón de acceso (lectura, escritura, agregación, latencia), después el motor, y solo al final el tamaño.

Si el enunciado dice…La respuesta apunta a…
"read-heavy reporting must not hit the primary"Read replicas (+ Aurora reader endpoint)
"key-value lookups in single-digit ms for millions of users"DynamoDB (+ DAX para caché)
"cache query results or sessions, sub-millisecond"ElastiCache for Redis
"MySQL compatibility with much higher throughput"Amazon Aurora (hasta 6x MySQL)
"thousands of Lambda functions exhaust DB connections"RDS Proxy (connection pooling)

Task Statement 4: Determine high-performing and/or scalable network architectures

Evalúa el placement de recursos y la topología. Para contenido HTTP global, CloudFront cachea en edge y acerca bytes al usuario; para tráfico TCP/UDP no HTTP (gaming, voz, IoT), Global Accelerator con IPs anycast estáticas que llevan al edge más cercano. En el balanceo, ALB enruta en capa 7 (por path o host, ideal para microservicios) y NLB en capa 4 (latencia mínima, millones de conexiones concurrentes, static IP). El diseño de subnets, rangos IP y route tables es parte del task statement, incluida la regla de oro de la latencia: el tráfico crítico entre capas se queda en la misma AZ, la alta disponibilidad la pone el balanceador. Y para alcanzar servicios de AWS o de otro VPC sin internet, VPC endpoints y PrivateLink. La señal maestra: cifras de latencia global → edge; routing por path → ALB; static IP y millones de flujos → NLB.

Si el enunciado dice…La respuesta apunta a…
"global users, HTTP content, lower latency"CloudFront (cache en edge)
"non-HTTP game or voice traffic to the nearest edge"Global Accelerator (anycast, IP estática)
"route by URL path to different microservices"ALB (path-based routing)
"millions of TCP connections, ultra-low latency, static IP"NLB (capa 4)
"reach an AWS service or another VPC privately"VPC endpoints / PrivateLink

Task Statement 5: Determine high-performing data ingestion and transformation solutions

Evalúa la ingesta según la frequency y el volumen. Tiempo real con orden por clave y posibilidad de replay → Kinesis Data Streams con shards (u on-demand); entregar a S3/Redshift/OpenSearch sin escribir código → Kinesis Data Firehose (con buffer configurable y transformación Lambda); ETL serverless con catálogo → Glue (crawlers, Data Catalog, csv a parquet); big data → EMR; consultar el lago → Athena; gobernarlo → Lake Formation; visualizarlo → QuickSight. El task statement incluye el caso puntual masivo (DataSync o AWS Snow según volumen y enlace) y la seguridad del punto de ingesta (API Gateway, PrivateLink). El patrón estrella del examen: convertir csv en parquet y particionar en S3 para que Athena escanee y cobre mucho menos.

Si el enunciado dice…La respuesta apunta a…
"ingest millions of events per second, ordered per key, with replay"Kinesis Data Streams (shards / on-demand)
"load streaming data into S3 with no custom code"Kinesis Data Firehose
"serverless ETL: transform csv to parquet and catalog it"AWS Glue (crawlers + Data Catalog)
"run Spark jobs over a data lake"EMR (o Glue para ETL serverless)
"dashboards on the data lake for business users"QuickSight
Para el examen
En D3 la respuesta se reconoce por la unidad del enunciado: IOPS garantizadas → io2; sub-millisecond → ElastiCache o DAX; prefijos y multipart → S3; shards → Kinesis; anycast y static IP → Global Accelerator; "per-key ordering" → Kinesis (no SQS estándar); "aggregate throughput" → FSx for Lustre o EFS. Si la pregunta incluye una cifra de latencia, throughput o conexiones, esa cifra es la pista: elimina los servicios que no la alcanzan de fábrica.

Repaso rápido: 5 preguntas de señal

Cinco escenarios con la métrica como pista; cada uno cae en un task statement distinto:

D3-R1 A team needs interactive queries over 10 TB of Parquet files in S3 with no servers to manage. Which service fits?
Amazon Athena
SQL serverless sobre S3 que cobra por datos escaneados; Redshift exige un warehouse y EMR clusters.
D3-R2 Stateless web servers must share session data with sub-millisecond reads. Which solution improves performance?
ElastiCache for Redis
Caché in-memory compartida por todas las instancias; DynamoDB responde en milisegundos.
D3-R3 An HPC cluster needs a parallel file system with massive aggregate throughput in the same AZ. Which storage fits?
FSx for Lustre
Sistema de archivos paralelo para HPC; EFS es NFS compartido y S3 no se monta como filesystem.
D3-R4 Users worldwide report slow loading of a website's images and videos. What improves latency MOST?
Amazon CloudFront
Cachea el contenido en edge locations cercanas al usuario.
D3-R5 Producers send more data than the Kinesis data stream can ingest. Which action increases throughput?
Increase the shard count
Cada shard aporta capacidad propia de lectura/escritura; más shards (o modo on-demand) = más throughput.
Checkpoint — lo que debes recordar de D3
  1. Elige storage por patrón de acceso: objeto (S3), bloque (EBS), archivo (EFS/FSx).
  2. Rendimiento: S3 = prefijos y multipart; EBS = gp3/io2 con IOPS provisionadas; EFS = crece con los clientes.
  3. FSx for Lustre para HPC paralelo; FSx for Windows para SMB y Active Directory.
  4. Compute: familia c/m/r/i/p según CPU, equilibrio, memoria o GPU; subir la memoria de Lambda escala CPU y red.
  5. Desacoplar también es rendimiento: SQS/SNS dejan escalar cada componente a su ritmo.
  6. Read-heavy → read replicas + ElastiCache; DynamoDB + DAX para single-digit ms.
  7. Aurora hasta 6x MySQL, 6 copias del storage en 3 AZs, endpoints writer/reader.
  8. CloudFront cachea HTTP en edge; Global Accelerator para TCP/UDP con IPs anycast estáticas.
  9. ALB enruta capa 7 (paths/hosts); NLB capa 4 con latencia mínima y static IP.
  10. Ingesta: Kinesis (shards, orden, replay) para streams; Firehose entrega sin código; Glue transforma a parquet y abarata las consultas.
