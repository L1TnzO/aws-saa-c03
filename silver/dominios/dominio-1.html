El Dominio 1 evalúa la seguridad en tres capas que se corresponden una a una con sus tres task statements: el acceso (quién entra a la cuenta, con qué identidad y con qué permisos), las workloads y aplicaciones (cómo se exponen y se defienden en la red) y los datos (cómo se cifran, rotan, retienen y protegen). Con un 30% de peso equivale a unas 15 de las 50 preguntas que puntúan, así que dominar D1 es la inversión de mayor retorno de todo el examen. Las preguntas no describen pantallas de consola: te plantan un escenario con una señal en inglés — "employees already authenticate with the corporate directory", "credentials must not be stored in the source code" — y esperan que reconozcas el patrón y elijas el servicio correcto entre distractors plausibles.

Cómo estudiarlo: en capas, igual que se defiende una arquitectura real. Empieza por la identidad (IAM, STS, federación, multi-cuenta), porque además atraviesa los otros tres dominios; sigue con el perímetro de red (VPC, security groups, WAF, Shield); y cierra con los controles de datos (KMS, ACM, Macie, backups). Esta página es la vista de conjunto del dominio: cada task statement trae su tabla de señales del enunciado → respuesta, pensada como lista de cotejo para el repaso final. Cuando una fila no te suene, salta a la página de tema concreta en la ruta de estudio del final de esta página.

Task Statement 1: Design secure access to AWS resources

Este task statement mide si sabes construir el modelo de identity and access management de una cuenta y de una organización: usuarios, grupos, roles y políticas IAM bajo least privilege, federación del directorio corporativo con IAM Identity Center (antes AWS SSO), credenciales temporales vía AWS STS y role switching para el acceso entre cuentas, y el gobierno multi-cuenta con AWS Organizations, service control policies y Control Tower. Las decisiones de diseño que premia el examen son estables en el tiempo: las aplicaciones siempre asumen roles (nunca access keys embebidas), los humanos con identidad corporativa se federan (nunca se duplican como usuarios IAM), y los límites de toda la organización se aplican con SCPs, que solo restringen permisos sin conceder ninguno. Aquí también cae el shared responsibility model: tú respondes de la seguridad in the cloud; AWS de la seguridad of the cloud.

Si el enunciado dice…La respuesta apunta a…
"employees already authenticate with the corporate directory / Active Directory"Federación con IAM Identity Center (AWS SSO) + roles; nunca usuarios IAM duplicados
"an application running on EC2/Lambda needs access to S3/DynamoDB"IAM role (instance profile) con credenciales temporales de STS
"enforce guardrails across all accounts in the organization"AWS Organizations + SCPs; Control Tower como opción gestionada
"grant temporary access to an auditor for one week"IAM role + STS AssumeRole con trust policy
"permissions only on a specific bucket for one team"Least privilege + resource policy (S3 bucket policy)

Task Statement 2: Design secure workloads and applications

El segundo task statement traslada la seguridad al perímetro y a la aplicación. Mide el diseño de red con public and private subnets, security groups (stateful) frente a network ACLs (stateless), NAT gateways para la salida controlada de las subnets privadas, y la segmentación de la red. Sobre esa base integra los servicios que blindan lo expuesto: WAF contra ataques de capa 7 (SQL injection, XSS, rate-based), Shield frente a DDoS, Cognito para autenticar a los usuarios de apps web y móviles, y Secrets Manager para sacar credenciales del código. También evalúa las conexiones externas: Site-to-Site VPN cuando basta la internet pública, Direct Connect cuando hay requisitos de ancho de banda y privacidad, y VPC endpoints / PrivateLink para alcanzar servicios AWS sin cruzar internet. La decisión típica que premia el examen: todo lo que acepte tráfico del mundo va detrás de CloudFront + WAF; todo lo que no necesite IP pública, a subnets privadas.

Si el enunciado dice…La respuesta apunta a…
"protect a web application from SQL injection and cross-site scripting"AWS WAF (web ACL con managed rules) sobre CloudFront o ALB
"the application is under a volumetric DDoS attack"AWS Shield Advanced, con CloudFront y Route 53 como primera línea
"thousands of mobile users must sign up and sign in"Amazon Cognito user pools (JWT); identity pools para credenciales AWS
"database credentials must be rotated automatically"Secrets Manager con rotación programada (Lambda)
"hosts in private subnets need internet access for patches"NAT gateway en la subnet pública (egress only)

Task Statement 3: Determine appropriate data security controls

El tercer task statement baja al dato: cifrado en reposo y en tránsito, gestión de claves, rotación, retención y recuperación. Evalúa escoger KMS para el cifrado at rest con claves gestionadas por el cliente (SSE-KMS, key policies, rotación), distinguirlo de SSE-S3 y SSE-C, usar ACM para certificados TLS con renovación automática en ALB, CloudFront y API Gateway, y alinear los controles con los requisitos de cumplimiento: clasificación y descubrimiento de datos sensibles con Macie, retención con lifecycle de S3 e inmutabilidad con Object Lock, y recuperación con backups y replicación cross-region. Es el task statement del data governance: cuando el enunciado habla de compliance, auditoría de uso de claves o personal data, la respuesta casi siempre combina KMS + CloudTrail más el servicio de clasificación o retención que exija el requisito. Recuerda que el control de acceso al dato es doble: la política del recurso y la política de la clave KMS deben permitir la operación.

Si el enunciado dice…La respuesta apunta a…
"encrypt data at rest with customer-managed keys and audit key usage"SSE-KMS (KMS keys) + CloudTrail sobre la API de KMS
"TLS certificate on an internet-facing load balancer, renewed automatically"ACM: emisión y renovación automáticas (no importar a mano)
"discover and classify PII stored in S3"Amazon Macie
"keys must rotate every year without downtime"KMS con rotación automática anual (u on-demand)
"retain data 7 years for compliance, then delete"S3 lifecycle hacia Glacier / Deep Archive (+ Object Lock si exige inmutabilidad)
Para el examen
Las preguntas de D1 se responden en dos pasos: identifica la capa (¿habla de cuentas, permisos o identidades? → Task 1; ¿de puertos, apps expuestas o tráfico? → Task 2; ¿de cifrado, claves o PII? → Task 3) y aplica la regla por defecto de esa capa. Dos respuestas casi automáticas: una aplicación que necesita permisos siempre usa roles, y unos empleados con identidad corporativa siempre se federan. Los distractors típicos proponen usuarios IAM con access keys para apps o auditorías permanentes donde bastan credenciales temporales de STS.

Ruta de estudio de este dominio

Este dominio se repasa mejor en el orden en que se construye una defensa: identidad primero, perímetro después, datos al final. Las once páginas de tema del pack cubren los tres task statements completos; sigue la secuencia y trata cada tabla de señales como el test de salida de cada página:

  1. IAM: identidad y acceso — usuarios, grupos, roles, policies y STS: la base del Task 1.
  2. Organizations y multi-cuenta — SCPs, Control Tower y guardrails de organización.
  3. VPC, subnets y rutas — la segmentación pública/privada del Task 2.
  4. SG, NACL y NAT — stateful vs stateless y el egress controlado.
  5. TGW, peering, PrivateLink, DX/VPN — conexiones privadas hacia y desde AWS.
  6. KMS, ACM y cifrado — SSE-KMS, key policies, rotación y TLS: el Task 3.
  7. Secrets Manager y SSM — credenciales fuera del código, con rotación.
  8. Cognito — autenticación de usuarios de apps (user pools / identity pools).
  9. WAF y Shield — capa 7, rate limiting y DDoS.
  10. GuardDuty, Macie, Inspector — detección y clasificación de datos sensibles.
  11. CloudTrail y Config — la auditoría que exige todo requisito de cumplimiento.

Repaso rápido: 5 preguntas de señal

Cinco mini-escenarios con el formato real del examen: enunciado corto en inglés, respuesta y una línea de explicación. Si fallas una, vuelve a la página de tema correspondiente de la ruta anterior:

D1-R1 An application on an Amazon EC2 instance must upload files to an S3 bucket without storing long-term credentials. What is the MOST secure solution?
IAM role for EC2
Las apps asumen un rol (instance profile): STS entrega credenciales temporales y no hay access keys que rotar ni filtrar.
D1-R2 A company must prevent AWS Regions and services from being used across its 30 member accounts. Which mechanism meets this requirement?
SCPs in AWS Organizations
Los SCPs son guardrails de límite máximo que se aplican a toda la organización; las políticas IAM de una cuenta no cruzan esa frontera.
D1-R3 A public Application Load Balancer receives malicious requests that contain SQL injection patterns. Which service should a solutions architect deploy?
AWS WAF
WAF inspecciona HTTP/S (capa 7) con managed rules frente a SQLi y XSS; NACLs y SGs operan en capas 3/4.
D1-R4 Employees already sign in daily with corporate identities from the company directory. What is the MOST operationally efficient access strategy?
Federation with IAM Identity Center
Se federan las identidades existentes (SSO) y se asignan permisos con roles: cero usuarios IAM duplicados que mantener.
D1-R5 A security team must discover and classify personally identifiable information stored across terabytes of S3 data. Which service does this?
Amazon Macie
Macie usa machine learning para detectar y clasificar datos sensibles en S3 a escala; GuardDuty detecta amenazas, no contenido.
Checkpoint — lo que debes recordar de D1
  1. Least privilege es la respuesta por defecto de toda pregunta de permisos.
  2. Las aplicaciones (EC2, Lambda, ECS) usan roles con credenciales temporales de STS, nunca usuarios con access keys.
  3. Humanos con identidad corporativa → federación con IAM Identity Center (AWS SSO), no usuarios duplicados.
  4. Multi-cuenta → Organizations + SCPs; Control Tower cuando pidan la opción gestionada y con landing zone.
  5. Perímetro: subnets públicas/privadas; SG stateful en la instancia, NACL stateless en la subnet, NAT gateway solo para salir.
  6. WAF protege capa 7 (SQLi, XSS, rate-based); Shield cubre DDoS (Advanced con soporte y protección económica).
  7. Cognito: user pools autentican usuarios de la app (JWT); identity pools dan credenciales AWS temporales.
  8. Secrets Manager rota credenciales; Parameter Store SecureString basta para configuración no crítica.
  9. Cifrado: KMS para at rest (SSE-KMS + key policies + rotación); ACM para TLS con renovación automática.
  10. Macie descubre PII en S3 y CloudTrail audita cada API call: el combo que piden los requisitos de compliance.
