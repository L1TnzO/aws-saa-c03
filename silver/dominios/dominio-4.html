El Dominio 4 recorre las mismas familias que D3 — storage, compute, base de datos y red — pero con la lente del coste, y compone un 20% del examen: unas 10 de las 50 preguntas evaluadas. Sus cuatro task statements comparten un núcleo común de cost management: Cost Explorer para analizar, Budgets para alertar (y actuar con acciones de IAM), el Cost and Usage Report (CUR) para el máximo detalle en S3, y las cost allocation tags con multi-account billing para atribuir el gasto. Sobre ese núcleo, cada task statement aplica las palancas de su familia: tiering y lifecycle en storage, purchasing options y serverless en compute, motor y formato en bases de datos, y peajes de transferencia en red.

Cómo estudiarlo: es el dominio más rentable por minuto de estudio, porque los palancas se repiten: right-size (medir y ajustar tamaño), tiering (mover el dato al nivel barato), compromiso (Savings Plans/RI para carga estable), serverless (pagar por uso, no por capacidad) y minimizar la transferencia de datos (evitar NAT, usar endpoints y CDN). Aprende primero las cinco herramientas de visibilidad (una sola página del pack las cubre todas) y después las palancas por familia con las tablas de señales de esta página. En el examen, el calificativo "MOST cost-effective" casi siempre elimina las opciones sobredimensionadas y premia la más simple que cumple el requisito.

Task Statement 1: Design cost-optimized storage solutions

Evalúa mover cada byte al nivel más barato que su patrón de acceso permita. En S3: storage tiering con Intelligent-Tiering cuando el patrón es desconocido o cambia, lifecycle hacia Glacier Flexible Retrieval o Glacier Deep Archive para archivo, y Requester Pays cuando el que descarga es un tercero. En bloque: gp3 como valor por defecto (más rendimiento de línea base por GiB que gp2), HDD st1/sc1 para throughput secuencial barato (nunca como volumen de arranque) y right-sizing medido con CloudWatch. El task statement añade los data lifecycles, el storage auto scaling cuando el crecimiento es impredecible, las estrategias de backup (retención y frecuencia ajustadas al requisito), los batch uploads frente a subidas individuales, y la vía de transferencia más barata al mover datos a AWS (DataSync para sincronización online; appliances Snow cuando el volumen es masivo y el enlace lento).

Si el enunciado dice…La respuesta apunta a…
"access patterns are unknown or change over time"S3 Intelligent-Tiering (sin coste de retrieval)
"archive compliance data for 7 years at the lowest cost"S3 lifecycle → Glacier Deep Archive
"external partners download large datasets; owner must not pay egress"S3 bucket con Requester Pays
"an EBS volume is 80% idle but peaks monthly"Right-size a gp3 midiendo con CloudWatch; snapshots incrementales
"backup retention grows without control"AWS Backup con lifecycle y retención definidas

Task Statement 2: Design cost-optimized compute solutions

Evalúa casar el modelo de compra con la predictibilidad de la carga: On-Demand para lo impredecible, Spot para lo interrumpible con el mayor descuento, y Savings Plans / Reserved Instances para uso estable comprometido a 1 o 3 años (no se apilan con Spot). La segunda palanca es serverless: Lambda y Fargate facturan por uso, así que las cargas esporádicas o intermitentes pagan cero en reposo. La tercera es la utilization: right-sizing con Compute Optimizer, auto scaling para no mantener capacidad ociosa, densidad con contenedores, y hibernation o stop programado para entornos no productivos que solo trabajan ocho horas al día. El task statement incluye el coste según la clase de workload (producción multi-AZ frente a no-producción más laxa), la estrategia de balanceo (ALB/NLB/GWLB según capa) y las opciones híbridas (Outposts, Snowball Edge) cuando el compute debe vivir on-premises.

Si el enunciado dice…La respuesta apunta a…
"a fault-tolerant batch job can be interrupted; lowest cost"Spot Instances (con ASG o gestionadas por Batch)
"steady 24/7 production workload for 1-3 years"Savings Plans o Reserved Instances
"sporadic workloads with days of zero traffic"Lambda / Fargate (facturación por uso, sin idle)
"dev environment used 8 hours a day, fast resume needed"Stop/start programado o EC2 hibernation
"instance size is a guess; usage is unknown"Right-sizing con Compute Optimizer + auto scaling

Task Statement 3: Design cost-optimized database solutions

Evalúa el motor y el formato que la carga realmente necesita. Carga relacional intermitente o impredecible → Aurora Serverless (paga por ACUs de consumo); key-value con picos difíciles de prever → DynamoDB en modo on-demand; carga estable → RDS/Aurora con capacidad reservada; analítica pesada sobre columnas → formato columnar (Redshift) en lugar de escanear un motor transaccional; series temporales → motor purpose-built. El caching reduce el load sobre el recurso más caro (ElastiCache delante de RDS), las data retention policies evitan que backups y snapshots crezcan sin control (frecuencia y retención ajustadas al requisito), y las migraciones — homogéneas directas, heterogéneas con DMS + Schema Conversion — también aparecen como palanca de coste al cambiar de motor. La decisión maestra: primero si el workload es intermitente (serverless), luego si el patrón es analítico (columnar), y solo al final el tamaño de la instancia.

Si el enunciado dice…La respuesta apunta a…
"intermittent, unpredictable relational load; pay only when used"Aurora Serverless v2 (ACUs)
"spiky key-value traffic, capacity impossible to forecast"DynamoDB on-demand
"repeated identical queries inflate the RDS bill"ElastiCache delante de la base de datos
"heavy scans over a few columns of TB of data"Redshift (columnar) o Athena sobre parquet
"snapshots and backups accumulate cost"Políticas de retención y frecuencia (AWS Backup)

Task Statement 4: Design cost-optimized network architectures

Evalúa el peaje invisible de la transferencia de datos. El tráfico AZ-to-AZ y Region-to-Region se cobra, y el NAT gateway añade coste de procesamiento por GB: de ahí dos patrones premiados — el gateway VPC endpoint para S3 y DynamoDB (gratis y sin pasar por el NAT) y un NAT gateway por AZ para que el tráfico de cada AZ salga por su propia puerta en vez de cruzar la AZ (que además añade HA). Para servir contenido al mundo, CloudFront cachea y entrega desde el edge, lo que suele abaratar el egress frente a servir todo desde una región; para IPs estáticas globales, Global Accelerator. En conectividad privada: la VPN es la opción barata sobre internet, Direct Connect la dedicada que se justifica por volumen y predecibilidad; entre VPCs, peering para pocos pares y Transit Gateway para topologías grandes. El task statement cierra con estrategias de throttling y con el ancho de banda adecuado (una VPN o varias, la velocidad del Direct Connect).

Si el enunciado dice…La respuesta apunta a…
"reduce NAT gateway data processing for S3-bound traffic"Gateway VPC endpoint para S3 (sin coste de procesamiento)
"three AZs all egress through a single NAT gateway"Un NAT gateway por AZ (evita peaje cross-AZ y añade HA)
"global users download content; serving from S3 is expensive"CloudFront entrega desde el edge
"private connectivity needed but budget is tight"Site-to-Site VPN sobre internet (Direct Connect si el volumen lo justifica)
"inter-AZ traffic between app and DB is billed"Co-locar capas en la misma AZ donde la latencia lo permita
Para el examen
Cuando el enunciado pida "MOST cost-effective", aplica el mantra en orden: right-size (¿está sobredimensionado?), tier (¿el dato puede bajar de nivel?), commit (¿la carga es estable?), serverless (¿es intermitente?) y minimize data transfer (¿paga NAT o cross-AZ sin necesidad?). Los distractors típicos mezclan availability con coste: proponen multi-region o Multi-AZ donde el requisito no lo pide — en D4, pagar resiliencia que el negocio no pidió es la respuesta incorrecta.

Repaso rápido: 5 preguntas de señal

Cinco escenarios típicos de D4 en inglés, con su respuesta y una línea de razonamiento. Todos se resuelven con una de las palancas del mapa:

D4-R1 A fault-tolerant analytics job can be interrupted with no data loss requirement. Which EC2 purchasing option minimizes cost?
Spot Instances
Cargas interrumpibles obtienen el mayor descuento con Spot; un Saving Plan compromete capacidad que aquí no hace falta.
D4-R2 A production application will run steadily 24/7 for the next 3 years. How can compute costs be reduced?
Savings Plans / Reserved Instances
El uso estable comprometido a 1 o 3 años se descuenta frente a On-Demand; Spot no encaja por las interrupciones.
D4-R3 Regulatory archives must be kept for 10 years and accessed almost never. Which S3 class is MOST cost-effective?
S3 Glacier Deep Archive
Es la clase de archivo más barata para retención de años con recuperaciones raras (horas de espera tolerables).
D4-R4 Private EC2 instances upload terabytes to S3 through a NAT gateway. How can data transfer costs be reduced?
Gateway VPC endpoint for S3
El endpoint de gateway para S3 no pasa por el NAT (ni paga su procesamiento por GB) y no sale a internet.
D4-R5 A relational database serves an invoicing app with unpredictable usage, idle nights and monthly peaks. Which option minimizes cost?
Aurora Serverless v2
Escala las ACUs con la demanda y factura por consumo: en reposo paga lo mínimo y en el pico crece sola.
Checkpoint — lo que debes recordar de D4
  1. Primero el driver del gasto: storage, compute, base de datos o transferencia — cada uno tiene sus palancas.
  2. S3: Intelligent-Tiering para patrones desconocidos; lifecycle hacia Glacier/Deep Archive para archivo barato.
  3. EBS: gp3 por defecto y right-size medido con CloudWatch; HDD st1/sc1 solo para throughput secuencial.
  4. Compute: On-Demand (impredecible), Spot (interrumpible), Savings Plans/RI (estable), serverless (esporádico).
  5. El overprovisioning es la fuga número uno: auto scaling y Compute Optimizer la cierran.
  6. Bases de datos: Aurora Serverless y DynamoDB on-demand para lo intermitente; ElastiCache para no tocar el motor caro.
  7. Backups y snapshots también se optimizan: retención y frecuencia ajustadas al requisito.
  8. Gateway VPC endpoint de S3/DynamoDB: gratis y evita el peaje del NAT gateway.
  9. El tráfico cross-AZ y cross-region se cobra: un NAT gateway por AZ y CloudFront para servir al mundo.
  10. Visibilidad primero: Cost Explorer + Budgets + CUR + tags; no optimices lo que no puedes ver.
